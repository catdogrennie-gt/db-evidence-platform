# Zabbix 自动巡检改造：实际验收记录

本轮扩展独立平台，复用已有授权、证据、事件、调查与任务域。验证对象为个人隔离环境中的实际 Zabbix、MySQL 控制库和独立 [SignalLens-Lab](https://github.com/catdogrennie-gt/SignalLens-Lab)；目标业务数据为合成数据。

**当前状态：按当前版本收尾。来源、权限、冻结、迁移、限定并发及一次自动周期的真实锁分析通过指定核对，最终代码回归完成。** SQL 窗口差分及大窗口曲线预算修复尚未完成，以下矩阵不表示所有需求已经验收。

记录日期：2026-11-08。原始 API 响应、冻结摘要、Lab 清理记录和模型 trace 保存在仓库外的私密运行目录；本文件公开检查方法、结果与边界，不附带账号、Token、目标地址或运行数据库。

## 权限对照：允许读取与隐藏业务范围

本轮在调查记录和问题详情两个入口各检查四种身份，共 8 项 HTTP 请求：

| 验收身份 | 调查记录 | 问题详情 | 含义 |
| --- | --- | --- | --- |
| `operator` | 200 | 200 | 有当前业务范围授权 |
| `viewer` | 200 | 200 | 只读身份在其授权范围内可查看 |
| `other` | 404 | 404 | 其他业务范围不暴露该对象 |
| `admin` | 403 | 403 | 控制面管理员未获得业务读取权 |

这是实际选定对象与身份的对照，不能替代全部角色 / 动作组合。正常业务范围读取、跨对象报告权限、冻结引用和每次模型 / 工具调用检查还由代码回归覆盖；撤权中断等情形的真实外部调用对照仍需单列，不能从这 8 项推断已经全部执行。

## 冻结与持久化怎么核对

选取已完成调查，按清单项 ID、类型、对象和 payload / payload hash 生成规范化摘要。第一次保留 843 个清单项与其中 8 个冻结外部窗口；等待实际采集产生晚于报告窗口的新资料后再次读取，确认：

1. Manifest 身份与全部清单项摘要相同。
2. 上游实际观测时间已经继续推进，比较的是新采样出现后的旧报告。
3. 冻结资料仍属于原对象与原窗口，当前指标查询另走当前来源。

服务重启另对比已有策略及运行记录，没有重建控制库或用新假数据替代。它们分别证明“旧依据不随新历史改变”和“状态跨进程保存”；不证明证据已经永久保留或整套备份恢复通过。

## 真实 MySQL 并发检查

### 选择与采集锁序

回归先复现选择映射与采集交叉持锁导致的 MySQL 1213，再统一 Instance → Mapping 的锁方向。真实用例让采集事务先持有 Instance 锁，再让选择事务进入其 Instance 加锁路径；要求采集能够完成映射更新、选择能够继续，两个事务最终回滚并清理精确夹具。

公开回归入口为 [test_monitoring_reports.py](../tests/platform/test_monitoring_reports.py) 中的 `test_real_mysql_selection_wait_does_not_block_collector_mapping_update`。它需要显式真实 MySQL 开关，使用合成发现结果与真实数据库行锁，不联系 Zabbix。同行的来源健康与过期任务 wrapper 用例是隔离回归，不混称真实数据库检查。

### 五轮、多进程派发

独立验收在真实 MySQL 上建立合成策略与对象，使用屏障使每轮两个新进程实际重叠，调用原派发域函数，持久检查预算预留、Investigation 和 Task：

| 轮次 | 预期与实际 |
| --- | --- |
| 首周期 | 只生成 1 份派发与调查 |
| 同周期重扫 | 不新增派发 |
| 第二周期，新进程 | 再新增 1 份派发，总数为 2 |
| 第二周期重扫 | 总数仍为 2 |
| 第三周期 | `budget_exhausted`，总数仍为 2 |

到期时间由验收夹具人工推进，AI 任务延后以隔离派发检查。模型调用、工具调用和目标采集均为 0；没有把这项检查称为真实周期等待或完整 AI 执行。清理按本次新建主键沿依赖关系追踪，遍历模型元数据中的表并核对本次相关记录无残留，没有按名称模糊删除或清空原业务数据。

当前已回查的多进程记录对应源码快照 `e842e02`，五轮均通过。最终源码收口后的短复跑仍待补；这项记录不自动覆盖后续修改。

## Lab 实际负载与清理

三个锁实验与一个 SQL 压力实验分别保留以下观测阶段：

| 阶段 | 每次实验样本数 | 用途 |
| --- | --- | --- |
| `baseline` | 3 | 故障前参照 |
| `fault` | 23 | 故障 / 压力期间观测 |
| `negative_control` | 1 | 无效动作对照，不能说成有效处置 |
| `recovery` | 5 | 结束负载后的实际观察 |

45 秒是故障 / 负载阶段时长，完整实验还包含基线、恢复与清理。每次清理均核对演练 worker 停止、事务回滚及连接关闭、残留演练会话为 0、残留锁等待为 0，数据摘要与起点一致。

SQL 压力的 CPU 数值是 VM 主机观测，不能全部归因于某条 SQL。`threads_running=4`、QPS 和探针耗时说明实际负载变化，不替代语句级窗口差分。当前实际 SQL 摘要缺少可验证的 counter epoch，累计耗时或生命周期最大值不能当作该窗口的平均 / 最大耗时；本轮未验收 SQL 窗口延迟差分与根因诊断。

Lab 负责受控故障与清理，平台负责观测与分析；这不是平台自动修复数据库的记录。
