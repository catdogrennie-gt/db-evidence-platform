这是工程实施顺序，综合常见运维场景、业务影响、可采数据与本机成本排序，**不是行业故障频率统计**。“未告警”指当时实际配置没有产生对应告警，不能理解为 Zabbix 天生不能实现。每项都要保存触发器、宏和实际事件作对照；如已有告警，记录为“已有告警，补充关联解释”，不算新增发现。

## 每轮开始前先准备

先写清本轮要验证到哪一层：发现现象、判断影响、关联原因，还是验证恢复。不能因为已有一个相关数值，就默认具备判断完整根因的条件。

| 检查项 | 开始前应有的记录 |
| --- | --- |
| 必需信息 | 要判断该现象及原因必须有哪些指标、快照或日志；可选辅助信息另列 |
| 实际接入 | 来源、主机和监控项是否已选入同一联合对象，数据是否可读、有样本 |
| 数据有效性 | 单位、计数/速率及标签语义、采样周期、实际采样时间、重置和缺口是否明确，相关数据是否能对齐；数值可读不等于足够新鲜 |
| 范围与权限 | 数据及模型外发是否授权，任务选择是否仍有效，是否混入已移除项 |
| 发现流程预演 | 正常采样 → 预期变化 → 自主检查 → 证据冻结 → 分析展示 → 后续恢复采样；检查调度和窗口是否能覆盖 |
| 继续或跳过 | 关键项可从 Zabbix 补接则先补；无法补齐则记录缺项和替代验证范围，不开启无条件验收的故障 |

顺序固定为 **信息需求 → 接入/时效/语义/权限检查 → 自然发现、分析、关闭恢复的流程预演 → GO / SKIP → ON**。预演包括调度、冻结窗口和临时加速的还原；不能先开问题再等待未知条件。前提不能满足时显式标 `SKIP`，说明缺项和可验证范围，不把未执行记为通过。

**准备中发现的平台不足：** 旧未选项可能进入新自主分析范围，已修选择快照和冻结过滤，并完成本地、真实数据只读及部署检查。随后的实际锁等待重测确认新报告仅使用所选项，同时暴露采样数量表述不足，继续改进。发现逻辑中部分旧诊断来源的短期残留仍需后续检查，不能把“模型输入范围已修复”写成全部发现语义已经完成。

## 每项如何判定

1. **采集成立：** Zabbix 保存了实际样本，名称、单位、时间和缺口可查。
2. **对照成立：** 保存当时启用的模板/宏/触发器和事件，确认是未覆盖、尚未触发，还是已经告警。
3. **发现成立：** B 自身普通巡检或周期分析建立问题/待核验假设；A 和验收脚本没有提交分析任务或答案。
4. **解释成立：** 报告引用实际证据，解释现象、原因及反证，并给出合理操作；结论未知时如实说明。
5. **恢复成立：** 直接负载已停止；后续上游样本支持恢复。直接清理成功和监控恢复分别记。

所有公开结果必须标明实际验证日期与版本，单次成功不代表通用准确率。没有完成的项保留原状态，不用页面“完成”动画代替验收。

## 7–12项的实施评估与准入门槛

以下是 **2026-11-12 根据当前源码作出的下一批实施方案，不是运行通过记录**。首批1–6的实测状态以上表和对应记录为准。7–12尚未成为可启动的Lab场景，完成固定负载、采集契约与关闭清理后，才能加入A的可用目录。

### 现有基础与共同边界

新Lab的 `compose.evolution.yaml` 与 `compose.replica.yaml` 合计定义4个MySQL、3个应用：每库600MiB/0.7CPU、每应用160MiB/0.3CPU，**配置硬上限合计2880MiB/3.7CPU，不能理解为当前空闲资源或实际占用**。数据库 buffer pool 为96MiB、最大连接40；应用池6、队列24、两个消费者，单条查询上限1200ms，连接/读写超时3秒。初始化业务表每库4000行，现有小表不能证明缓存失效或真实存储瓶颈。

现成的 `/metrics` 包含请求/DB调用耗时、错误、池和队列；`/database` 包含连接、事务、SQL扫描与临时表等诊断。**新场景缺的指标须先经Zabbix补采，B仍只读Zabbix，不能另接一条故障答案通道。** 每项应有来源、host/item身份、单位、采样时间/周期和 `gauge/rate/counter` 语义；累计计数按有效窗口差分，实例重启或计数重置时该窗口为未知。

实施顺序建议为 **12 → 9 → 8 → 11**；10先积累真实数据，7满足隔离条件后再决定。每次只开启一个实验，沿用单owner、重复ON不叠加、失联租约到期停止和OFF直接清理。新增数据仍受5GiB总预算约束；**Compose目前没有数据卷容量硬配额**，增加写入场景前须补字节/行数上限、剩余空间检查和自动止写，不能把预算文字当作已经实现的保护。

### 7. 存储路径变慢：先补证据，暂缓故障注入

- **收益与可行性：** 能区分“SQL本身低效”和“等待存储”，但当前库共用VM存储，尚不能证明块设备隔离、限速生效及对其他服务无影响。现阶段不运行磁盘压力或修改宿主磁盘策略。
- **建议最小复现：** 将来在专用测试卷/目标容器中，先得到稳定物理读基线，再施加固定容器IO限速；保持相同查询与请求量，最多两个查询worker，沿用SQL超时，独立数据不超过256MiB。开始前核实内核IO控制器、设备映射、实际读字节和现有服务延迟；任一不成立即跳过注入。
- **采集契约：** OS设备IO时延/队列及实际读写量，配合MySQL文件IO计数/等待窗口、SQL耗时、应用耗时和CPU反证。MySQL文件等待可以只读聚合采集，计时单位和重置窗口必须保留，文件绝对路径不发给模型。[MySQL文件IO汇总](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-file-summary-tables.html)
- **验收与替代范围：** Docker IO控制依赖实际设备与运行方式，不能只改一个配置值就算限速成功。[Docker运行参数](https://docs.docker.com/engine/containers/run/) 进一步推导：容器限流也不必然使共享设备的await升高；只能按实际证据称“测试容器存储路径受限”，不能认定硬件故障。条件不足时只验证文件等待的采集、单位和报告引用，**不计作IO故障识别通过**。

### 8. 工作集扩大：P2，可在本机有界实施

- **收益与最小复现：** 复用业务测试库，另外预置192–256MiB的只读测试表；先反复读小热区，再以相同并发/请求量读取较大范围。保持索引、SQL形状、buffer pool配置一致，避免把查询改写或流量增加误当缓存原因。不清空VM页缓存，不重启现有数据库，不修改全局buffer pool。
- **资源与采集：** 额外数据预算不超过256MiB，沿用现有DB容器内存/CPU上限、两个worker和SQL超时。至少采 `Innodb_buffer_pool_reads`、`Innodb_buffer_pool_read_requests`、请求量、SQL/应用耗时、物理读及CPU/锁反证。缓存命中变化按同一有效时间窗计算，不能拿启动以来的累计比例代替当前表现。[MySQL状态变量](https://dev.mysql.com/doc/refman/8.4/en/server-status-variables.html)
- **准入与通过门槛：** 当前 `/database` 尚无该组buffer计数，需先补采和重置检测。数据落盘大小大于buffer pool仍不等于发生物理读；必须观察到实际读代价变化。若操作系统缓存使IO变化不明显，只记录“工作集访问变化”，不强行认定磁盘瓶颈。关闭后恢复小热区访问，重新热身后的样本用于复验，不能承诺立即恢复原命中率。

### 9. 连接抖动与认证错误：P1，分两个小实验

- **收益与最小复现：** 总连接数可能始终很低，却出现频繁握手或请求失败。先让一个worker以最多2次/秒建立并正常关闭短连接，保持同时连接不超过2；再单独测试固定合成身份的已知错误认证，最多1次/秒、每次实验最多20次。两者不能混在一个结论中。
- **资源与采集：** 复用隔离业务库，新增测试账号并限制并发，不借用管理员/监控账号。补应用连接尝试/成功/失败、获取连接耗时、实际错误码，联合 `Connections`、`Threads_connected`、`Aborted_connects`、`Aborted_clients` 及请求失败率；分别标明累计计数与窗口速率。监控自身产生的连接计入正常基线。
- **准入与安全：** 现有应用复用固定连接池，未实现上述短连接/认证模式及细分计数，须增加固定模式后再接入A；不接受访客输入账号、地址、口令或速率。只记录脱敏错误分类，不导出密码、来源个人信息或原始认证日志。
- **通过与反证：** 认证失败应有真实错误码支持；`Aborted_connects` 还可能来自其他连接问题，不能单凭它断言口令错误。[MySQL连接错误说明](https://dev.mysql.com/doc/refman/8.4/en/communication-errors.html) 成功短连接若未造成业务影响，合理结果可以是“连接行为变化，尚无故障证据”，不能为演示强造故障。OFF后停止尝试，速率/错误新增量回落，累计总数不会归零。

### 10. 容量增长：P3，增长观察与耗尽预测分开

- **先做的可行范围：** 先记录真实空间余量、业务表/日志大小、写入量与清理事件；在单独测试表中采用固定小批量写入，例如每分钟最多2MiB、累计最多64MiB，达到任一上限或空间门槛即止写。只能由Lab固定执行器写入，AI没有写权限。预算和止写保护实现前只读观察，不制造增长。
- **尚缺的条件：** 当前普通自动调查窗口为近1小时，每项历史还有返回预算；不能据此直接宣称具备跨天容量预测。需先补长窗口查询/有说明的降采样、有效样本数、计数重置及定期清理识别。至少积累6–24小时真实数据，并证明观察到的增长相对稳定，才评估条件性的耗尽时间；这个时长是本项目建议门槛，不是精度保证。
- **安全与采集：** 当前卷没有硬容量配额，也存在数据库日志增长，不能用填满VM磁盘制造红色看板。不改时钟、不压缩横轴伪造天数、不把虚构的小磁盘容量换算成宿主机耗尽时间；单独测试卷若有配额，必须明确它只是实验容量。记录字节单位、可用空间来源、增长窗口和保留策略。
- **可交付与暂缓理由：** 首先验证“窗口内持续增长及来源解释”，未到容量阈值也可给出待核验风险。长窗、空间隔离或清理模型不成立时，暂缓“预计多久耗尽”的公开演示；OFF表示停止新增写入，不表示文件立刻缩小。测试数据后续回收由人工维护，不通过删除真实监控历史掩盖增长。

### 11. 网络路径延时：P2先做抖动，重试放大另行验收

- **最小复现与收益：** 在独立测试应用到固定DB之间加一个只连接该DB的TCP代理，先保持代理无附加延时形成基线，再固定注入如100ms延时、50ms抖动，观察应用DB调用与服务端SQL耗时的差异。可用 [Toxiproxy](https://github.com/Shopify/toxiproxy) 的单向延时功能；延时方向需记录，不能把单向参数直接当往返时延。
- **资源与安全：** 建议代理额外上限64MiB/0.1CPU；如需复制应用则再预算160MiB/0.3CPU，均为待实现准入值。控制API仅内部可达、目的地址固定，不能成为公网任意TCP代理。默认不授予应用 `NET_ADMIN`，不改VM/Windows网卡、全局防火墙或Zabbix网络。
- **采集契约与缺口：** 关联应用请求/DB调用尾延迟、连接错误、独立路径探测和MySQL服务端耗时/负载。当前应用没有业务重试策略和重试计数；先验证路径延时，不能把第4项应用sleep排队冒充网络故障。随后若新增重试，只对幂等读、最多额外1次、固定退避及3秒总期限，并采重试次数，才验“重试放大”。
- **通过门槛：** B应根据实际两端计时给出路径问题的候选解释，并保留服务端正常反证；不能从代理注入标记直接得知答案，也不能认定真实链路丢包或运营商故障。OFF移除该目标的附加延时，保持代理连通，再等后续实际采样恢复。

### 12. 停更与旧正常值：P1，成本最低且直接影响结论可信度

- **最小复现：** 新增独立5秒心跳测试项，正常记录实际心跳/采样时间至少90秒，再仅停止其发送进程60–90秒；其他主机、数据库与Zabbix持续运行。恢复进程后等待新样本，不写回历史时间。另设“值不变但按心跳保存”的正常对照，验证平台不会把合法稀疏历史当采集故障。
- **采集契约与资源：** 无需新增数据库，建议发送器不超过32MiB/0.05CPU。保存 item 的最新采样时间、约定周期、discard/heartbeat预处理、unsupported状态及API错误。必须区分“来源连通”“该项有新样本”“旧报告窗口有效”三件事；不能用平台请求成功时间刷新上游样本时间。
- **对照与平台改进门槛：** Zabbix本身支持 `nodata()`，不能宣称它无法发现停更。[Zabbix历史函数](https://www.zabbix.com/documentation/7.0/en/manual/appendix/functions/history) 稀疏历史还受预处理保存策略影响。[Zabbix预处理](https://www.zabbix.com/documentation/7.0/en/manual/config/items/preprocessing) 核对实际触发器后，分别记为已有告警的补充解释，或本配置缺少数据质量提示。平台应显示缺口/未知、标识旧报告，并考虑产生独立的数据质量待办，而非直接认定DB故障。
- **验收边界：** 本轮已有停更/选择变化的程序回归防护，尚未完成此项真实发送器→Zabbix→自主巡检全链路。若只做到UI不显示旧正常值，记为“状态正确，尚无自主数据质量发现”；不能将程序测试或手动发起报告计作该场景通过。

### 每项验证都要推动一次改进闭环

采用 **实际复现 → 查采集/发现/解释/展示缺口 → 修改对应平台能力 → 用相同条件和正常反证重测 → 单项发布**。不是只给场景打分，也不把诊断写进验收脚本帮助平台过关。逐项模板、本轮已修的程序缺口及其验证层次见[平台验证与改进记录](platform-evolution.md)。

每个新场景发布前都要更新本表、操作手册、Lab场景可用状态及版本说明；先在独立验证B完成验收，再按[版本切换说明](deployment-releases.md)切换。原公网目标和旧版本保持可用，发布后的入口、只读查看与写入拒绝必须再查一次。
