## 官方监控与实际数据

环境为 Zabbix 7.0.32、Agent 2 7.0.32、MySQL 8.4。使用原样官方 **Linux by Zabbix agent** 与 **MySQL by Zabbix agent 2** 模板，分别发现 75、52 个 items。另有独立的 3 项只读诊断扩展：锁等待数、锁链快照和归一化 SQL 摘要；没有修改官方模板。

既有只读来源可以发现这 130 项。CPU、内存、文件系统、查询活动、连接线程和诊断代表项的连续两轮 history 时间实际推进。模板项数不等于全部项都有历史：部分原始 master items 不保留历史，部分依赖计算需要更长基线，仍按实际状态显示。

官方参考：[MySQL 监控步骤](https://www.zabbix.com/documentation/7.0/en/manual/quickstart/monitor_mysql)、[MySQL Agent 2 模板](https://github.com/zabbix/zabbix/blob/7.0.32/templates/db/mysql_agent2/template_db_mysql_agent2.yaml)、[Linux 模板](https://github.com/zabbix/zabbix/blob/7.0.32/templates/os/linux/template_os_linux.yaml)。

监控账号可读所需 performance_schema，业务表 SELECT 被拒绝。Lab 的自签名 TLS 链路有加密，但未验证服务端身份，不能作为生产 TLS 配置范例。密码、配置、SQL 备份及原始验收资料均保存在仓库外。

## 模型与预算验证

第一次新组自动分析保留为失败记录：两次真实提供商请求完成，但旧上下文裁剪移除了全部证据，模型返回没有引用的事实，被报告校验拒绝。这不算有效诊断。

本轮修复使用有界数值表，保留每条序列的真实首末值、极值、时间与独立冻结引用；大工具结果按冻结样本摘要返回。摘要明确统计范围和截断，不能冒充全部原始历史。完整 22 项 / 18 条数值 / 两主机流程的提供商替身测试检查实际发送内容、引用和冻结工具返回；替身测试不算真实模型验收。

## 保留的边界

- 每个联合对象限定同一来源、同一业务系统，最多 32 项和 32 条人工登记关系。
- 通用文本或日志原文不会直接交给外部模型；专用诊断扩展只提供受约束的字段投影。自由说明和任意 key 参数不外发。
- SQL 摘要没有已验证的 reset epoch，不计算或声称窗口差分；累计 MAX 不当作窗口最大值。
- 主机关系是登记资料，曲线同时变化与模型假设均不足以证明因果。
- 本轮验证不覆盖生产规模、长期可靠性、高可用、任意模板的诊断准确率或自动修复。
