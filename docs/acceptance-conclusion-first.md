# 结论优先与 Zabbix 产品收敛验收

日期：2026-11-09。个人隔离 Lab，复用真实 Zabbix 观测；业务负载为合成负载。本轮没有再次注入故障。

## 产品结果

- 四个日常入口：问题分析、Zabbix 接入、数据查看、配置。来源连接、按 host / item / tags 选择、联合对象及数据下钻保留。
- 报告首先显示问题结论，再以三栏说明发生什么、为什么、现在怎么做。完整原因、引用、反证、操作前提与复验可展开；图表和分析过程随后按需阅读。
- 新部署默认 `zabbix_only`。旧直连、自定义采集模板与单 host 独立对象创建返回 410；调度及 worker 执行边界同时阻止旧采集任务。旧 ID 仍按权限只读回查，不替换成当前观测。
- 本机旧三个 Lab trapper 主机完成配置、类型化 history、trends 与控制库备份后移除；旧平台身份归档，旧发送容器停止。它们原先属于真实 Lab 采样，不将它们描述为伪造指标。官方 Linux / MySQL 及诊断扩展保留。

| v3.2 | 锁链、先后与 Uptime 的指定核对改善；实际已采集的小写锁结构字段未正确投影，部分建议字段来源不准确 | 修复既有白名单大小写读取、保持 HMAC 别名与冲突省略 |

实际新调查 `012149e5-60fb-4975-a475-0f714242f8d1`：一次 DeepSeek Pro 调用，6,555 input tokens、1,954 output tokens；完整请求连同预留开销 22,782 字节。两 host 的 **18 条数值序列全部进入本轮模型输入，预算省略为 0**；报告有 18 条冻结曲线。覆盖缺口仍保留，零预算省略不代表原始数据完整。

- 05:49:17.443118Z 的快照：阻塞事务 2364 → 等待事务 2369，原连接标识 4510 → 4561；请求侧 `RECORD / X,REC_NOT_GAP` 与来源相符。
- 报告不再将更早的空样本称为后续恢复，不断言瞬时、已恢复或当前仍等待。持锁时长、SQL、影响范围与联合根因保留未知。
- 表层机制明确为记录锁竞争；主机资源不能直接证明业务根因。建议为继续观察、在权限 / 标识映射 / 历史保留条件下进行人工只读关联，没有执行数据库变更。
- 嵌套支持、反证、操作引用均属于已提供的冻结清单；请求未突破字节、token、工具或调用上限。最终报告未调用额外工具，不把可用工具数写成实际使用次数。

**剩余语义限制：** 资源总结把 CPU、内存、负载、QPS、连接数笼统称为“低水平”，但 available-memory 是可用量，不宜与资源使用率统一这样表述；该段三个引用也没有分别覆盖其提及的所有指标。原句和引用保持原样，因此本轮只记录上述指定锁链与时间核对通过，**不宣称整份报告语义全通过**。例如实际 CPU 最小 / 最大为 2.7538% / 4.535491%，可用内存为 72.605743%–73.531443%，两种口径应分别解释。

锁表字段与连接标识核对参考 [data_locks](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-data-locks-table.html)、[data_lock_waits](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-data-lock-waits-table.html)、[threads](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-threads-table.html) 及仓库记录的[实际扩展查询](zabbix-official-setup.md)。
