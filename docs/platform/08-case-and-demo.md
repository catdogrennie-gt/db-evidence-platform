# 案例说明与演示路线

本案例展示一个内部 MySQL AI 运维平台的需求、设计、实现与验证。目标数据库为隔离合成环境；案例不代表企业生产部署。实际验证范围及未完成项见[验收记录](06-acceptance-status.md)。

## 1. 要解决的问题

数据库资料分散在监控、SQL 摘要、事务、日志、配置和人员记录中。只有聊天框缺少持续资料；只有指标图又难以解释某一次异常。平台把“责任范围、采集事实、时间窗、证据引用和处置结果”组织在一起，让 DBA、开发和审计人员按各自授权协作。

关键决策：数值历史交给 Prometheus；资产、权限、结构化证据与流程交给 MySQL；固定规则确定异常及复验结果；AI解释证据并提出待核验假设。采集与 AI 在不同进程运行，模型不能执行目标库变更。

## 2. 十五分钟演示路线

准备两种现有本地账号：平台管理员与有明确实例范围的 DBA。凭据在本机私密初始化资料中，演示文档不保存密码。不需要重新发起付费模型调用或注入故障。

| 时间 | 页面与动作 | 需要讲清的事实 |
| --- | --- | --- |
| 0–2分钟 | 先打开需求、架构图和页面流程，再登录工作台 | 平台由哪些部分组成，为什么采集、规则、模型和人工记录分开 |
| 2–4分钟 | 管理员查看资产目录与六步接入向导 | 已登记数量和启用状态不同；新数据库可以预检、核对身份、确认能力、配置采集并首采，不改代码 |
| 4–6分钟 | 查看管理员无观测资料权限提示，切换有范围的 DBA | 管理控制面不自动授予业务数据；账号目录、菜单与直接 API 均按后端范围裁剪 |
| 6–8分钟 | 打开实例指标、SQL、锁、结构、日志和主机页 | 绝对时间、单位、采集来源、不可用与不适用；曲线空点不是零，元数据行数是估计 |
| 8–10分钟 | 事件中心找到“持续锁等待”案例 | 连续样本触发规则，原始告警与事件处理分开；无数据不能自动恢复 |
| 10–12分钟 | 打开真实完成的 AI 调查及其中一条证据、冻结锁指标 | 事实、候选原因、反证、未知分开；引用回到同一冻结窗口，不拿当前状态替代历史 |
| 12–14分钟 | 对照无效处置和有效回滚的两个复验，再看已关闭事件 | SELECT 1 返回成功仍可能没有解决阻塞；只有新的有效样本满足条件，才能得到 improved |
| 14–15分钟 | 知识库查看事务阻塞案例、版本和来源清单 | 失败经验也沉淀；来源权限继续继承。自动化验收账号审核已明确标识，用户人工审阅另行进行 |

可选补充：库表索引页的固定单表 EXPLAIN 向导。只选择已采基本表、列和绑定值，提交持久任务后查看实际计划。平台不执行被解释的业务查询，不提供任意 SQL；估算计划变化不等于真实业务收益。

## 3. 已核验的事务阻塞案例

两次独立实验均在已核验身份的合成实例上使用现有行的锁定读，不修改行值。它们具有不同的事务标识和时间窗，不能混用。

第一次实验用于真实模型语义核查。持续采样确认单向等待链，DeepSeek 通过受限历史工具补证，报告引用五份证据及一个冻结 Prometheus 窗口。报告保留一次来源不可用的缺口，不能由缺失点推断锁已解除；没有循环等待证据，不能把阻塞直接写成死锁。

第二次实验走严格的处置顺序：

1. 后台规则发现持续超过阈值的真实等待链，形成事件。
2. 本地验收账号通过 HTTP 创建并审核无效方案，外部实验工具执行固定 SELECT 1；三个后续后台快照仍含相同等待链。
3. 后台确定性复验返回 `not_improved`，没有因为连通成功而关闭事件。
4. 再创建并审核准确释放实验阻塞事务的方案；外部工具实际执行 ROLLBACK，记录真实 UTC 时间。
5. 三个新的后台快照中目标等待链消失，复验返回 `improved`，事件以 `verified_recovery` 结案。
6. 关联事件、计划、两个复验、同类调查及受保护证据清单，创建、审核并发布知识版本。旧版保留、被新发布版本取代。

平台只保存外部执行记录和验证结果。自动化受控验收不冒充用户亲自审批，也不代表生产审批。锁链退出不证明业务恢复；时间相关性和已知实验安排不足以代替完整生产因果链。

## 4. 已核验的 SQL 索引案例

在三万行合成 orders 表上，对同一个 Schema、Digest、绑定值及 LIMIT 持续执行固定 0.5 QPS 查询。每个比较窗口至少持续三分钟，并保留三组真实后台摘要及来源证据。使用单实例、单摘要的显式 1ms 实验规则，不更改默认规则或把该阈值称为生产 SLO。

| 对照 | 实际观察 | 后台判定 |
| --- | --- | --- |
| 基线与无效 SELECT 1 后窗 | 平均耗时约 4.979 → 4.053 ms；调用率比约 1.004；未达到预先固定的至少 50% 耗时降低标准 | `not_improved`，不能把小幅波动写成“完全没有变化” |
| 无效后窗与新增 amount 索引后窗 | 平均耗时约 4.053 → 0.451 ms；调用率比约 0.992，前后各三组后台摘要 | `improved`，只覆盖该受控比较条件 |
| 固定模板 EXPLAIN | 实际后台只执行计划，由 `ALL`、约 30,284 行变为 `ref`、约 3 行 | 访问方式和行数是优化器估计，单独不证明真实收益 |

实验总计 281 次固定查询、零查询错误。平台保存方案、审核及外部执行记录；具备 UUID、专属索引名、列形状和 COMMENT 门禁的外部实验工具执行索引变更。正常收尾恢复原索引集合，并核对三万行有序数据 SHA256 未变；只禁用本次实验规则。独立超时回退工具与正常收尾分别记录，不把看门狗触发时刻当作实际回退完成时刻。

该案例经历过两次未通过的尝试：文件独占创建模式错误使首轮在负载前退出；第二轮将指标帧时间用作证据窗口上界，遗漏晚数毫秒的第三条来源，后台正确返回 `inconclusive`。修正实验工具为同时覆盖实际帧与证据时间后重新执行，没有修改规则、复验门槛或失败历史。新知识版本继承无效与有效两份冻结清单，标明自动化验收账号审核、用户尚未人工审阅。

小表合成查询、固定负载与受控索引不代表真实企业收益、业务恢复或普遍因果证明；不能外推生产准确率和百分比性能承诺。

## 5. 工程证据

- 新建第三个独立目标后经浏览器向导接入，未添加固定目标代码；八类来源持续后台运行。
- 按角色和实例范围执行真实 HTTP 检查，包含计数、联合对象、导出二次鉴权和即时撤权；新增功能继续补入矩阵。
- 真实单实例暂停时另一实例继续采集；采集进程中断后以新 attempt/fence 恢复，旧结果不能回填。
- 真实 TLS 成功与错误身份/信任失败分别验证，禁止无 SSL 能力时继续明文认证。
- 受保护事件与复验证据不依赖是否发起过 AI；清理失败不阻塞采集，旧资料的保留延长也生效。
- 新私密目录、独立控制库与端口从零初始化到空平台登录通过；复用了现有锁依赖虚拟环境与前端产物，不冒充全新操作系统安装测试。

查询和采集数据仅支持已记录的实际规模。五角色并发查询报告、三实例采样间隔和调度迁移缺口分别记录，不能从一次短测推导十实例容量或长期可用性。

## 6. 项目能力与验证概述

项目名称：**内部 MySQL AI 运维平台（隔离环境验证）**。以下概述仅覆盖文中已记录的工程实现与验证范围。

> 设计并实现基于 FastAPI、MySQL、Prometheus、React/TypeScript 的内部数据库运维平台，支持 MySQL 引导接入、持续多源采集、实例范围授权、历史查询及事件协作。
>
> 将 AI 调查与采集规则分离，通过冻结证据、受限只读工具、有效引用和调用预算辅助诊断；用真实事务阻塞的无效/有效处置对照验证流程，并沉淀版本化案例。
>
> 完成固定频率 SQL 索引实验，联合后台摘要、受限执行计划、无效检查对照与前后窗复验；保留失败尝试，并核验实验结束后的索引和数据完整性。
>
> 在三个独立 MySQL 合成目标上验证接入、故障隔离及进程恢复，执行多角色直接 HTTP 权限检查，保留实际性能、失败和未覆盖范围。

技术评审可按真实证据核对采用的事务隔离、租约、fence、来源有效性和授权策略。不要写“上线企业生产”“节省多少人力”“支持任意 SQL”“自动治愈数据库”或未经验证的准确率、规模及可用性。

## 7. 关键设计问题

| 问题 | 回答应包含的设计理由 |
| --- | --- |
| 为什么不让大模型直接连库？ | 凭据、任意查询、外发和变更风险无法靠提示词隔离；服务端固定工具、当前授权、冻结窗口及预算才是执行边界 |
| 为什么同时使用 MySQL 和 Prometheus？ | 一个处理资产、关系、状态、审计和证据对象，一个处理数值时序；报告需要把短保留时序物化到受保护清单 |
| 如何处理采集失败？ | 按来源报告失败和新鲜度，保留未知；单实例有限超时与退避，采集进程不等待模型，维护清理不阻塞队列 |
| 如何避免过期 worker 覆盖新结果？ | 控制库时间、持久任务/实例租约、attempt 和单调 fence；提交同事务再次校验配置、取消和期限 |
| 角色隔离的最小边界是什么？ | 实例集合与功能权限相交，联合对象检查全部来源；schema 选择不隔离底层全局会话/锁证据 |
| 如何证明修复有效？ | 固定可比前后窗、足够新样本、负向对照、明确判定条件；条件不足返回 inconclusive，不能把模型一句“恢复”当判据 |
| 下一步如何扩展 PostgreSQL？ | 单独实现身份、状态、SQL摘要、锁和日志适配及版本能力矩阵，沿用公共封套和授权；接口预留不等于已支持 |

验收记录中的剩余项是工程边界，应随版本和验证记录公开说明。后续优先补充对象/审计 TTL、更多数据库版本与权限组合、目标规模/采集开销和真实企业接入流程。
