# POOL-01：先补齐连接池联合分析的前提

## 验证什么

应用请求可能在获取连接时排队或超时，而 MySQL 全局仍有连接余量。判断时需要同时看到应用池容量、占用、排队和等待耗时、请求错误，以及数据库连接容量和当前用量；不能仅凭数据库连接数判断应用连接池是否充足。

这是联合解释候选，不预先认定 Zabbix 无法告警。本轮没有开启故障，实际触发器覆盖和异常结论仍待同窗对照。

## 本轮发现与改进

现有业务 A 对象已选满 32 项，但漏选池容量、占用与排队。Zabbix 中三项均可用，缺口出在平台的对象选择，而非上游没有采集。

通过现有运维账号和接入流程，新建 **业务 A · 请求与连接容量**：20 项、3 个来源主机、2 条登记关系。保留原 32 项对象和历史，没有增加选择上限、修改权限或重启服务。新对象仅准备数据，未建立自主分析策略，仍使用默认规则模式。

| 数据部分 | 实际核查 |
|---|---|
| 应用请求、池容量/占用/排队/等待及错误 | 已选择且自然采入；耗时单位为毫秒 |
| 数据库连接用量与容量 | 正常观察为约 10/40；这不是故障或全面健康判断 |
| 连接池正常对照 | 容量 6，观察时占用、排队和等待者为 0，错误率为 0 |
| 诊断和日志 | 应用事件、配置、错误、锁、会话、慢查询及事务共 7 类有近期采样；空快照不等于全窗口无问题 |
| 正常变化检查 | 5 分钟窗口的 11 个已知语义应用/数据库指标未发现持续基线偏离；两个主机项语义不足，未纳入此判断 |
| 只读展示 | 公网账号能打开新对象、查看补入三项的历史，配置写入被拒绝；本轮为 HTTP 验收 |

20 项均有自然采样，不等于历史覆盖完整或模型诊断通过。

## 模型输入与额度边界

使用真实正常数据做离线投影估算，在实际 AI 后台已配置的 48,000 字节输入限额内保留全部 13 个数值维度及 7 类诊断来源，估算约 31 KB。没有发送模型请求，也未完成正式冻结调查；故障和追加取证压力下的实际输入保留仍为 WAIT。

核查工具最初误用了 API 的旧 24 KB 配置，得到维度被挤出的结果；改用当前 AI 后台配置后纠正。没有调高任何运行预算，原检查结果留存为工具错误，不作为平台失败依据。

现有连接池策略 UTC 当日派发已达 **100/100**，其中 92 次周期派发、8 次异常派发；次数不是模型调用数或实际费用。当前不能再派发自主分析，本轮未开故障，也没有换账号或新策略绕过额度。原历史中的未知调用结果不重放。

针对五分钟周期分析过密，通过原有后端策略接口将该策略的常态 AI 间隔改为 **一小时**，五秒信号检查、异常触发、范围、外发许可及每日 100 次额度均保留。已读回配置并确认计数没有重置；未来是否减少重复分析与避免额度提前耗尽，仍需后续实际观察。这不构成对异常额度的保留保证。
