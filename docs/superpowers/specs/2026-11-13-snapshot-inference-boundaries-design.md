# 快照观察与恢复方式的解释边界

## 实际问题

旧真实报告已正确保留两份非空锁快照及后续空快照，却将后者描述为“自行恢复”，还混用了数值序列点数和快照数。空快照只能说明该次所保留观察没有等待，不能证明如何解除、连续时长或完整窗口的事故次数。历史报告和失败记录保持原样。

本轮 LOCK-03 使用当前封存版本重新做只读前提检查：锁快照、数量、时间、所选范围、权限和自然派发条件已具备；尚未完成新故障的资源/固定目标与独立清理复核，不开启故障。先修复可验证的解释输入缺口。

## 选择

不重复增加推理预算或重放旧模型调用；不靠字符串替换报告，也不将控制器动作传给模型作为答案。现有 chronology 只有 retained-samples 范围与计数，缺少类型和恢复机制的明确解释边界。

选择给平台生成的 chronology 增加一个固定、简短的语义契约：`sample_kind=point_in_time_snapshots`；样本数量仅属于本组保留快照；快照序列本身不建立解除机制、连续时长、事故次数或数值时间序列的总体样本分布。它不是本次故障的判定，也不宣称恢复或缺失；实际时间、数量、组边界与引用均不改变。

相较额外长提示词，契约随实际快照组出现；相较改输出验证器，不屏蔽原始模型错误；相较重写采集，只改模型输入表示。输入版本升级到 v4.8，模型权限、授权、冻结窗口和预算上限不变。工具预算不足仍可明确省略可选 chronology，不得为了保留说明而丢掉原证据。

## 验证与发布边界

先失败回归，再测试初始、最终和工具压缩中的契约、身份隔离、引用和数值/快照分离；真实模型请求的本地替代客户端只检验交付，不冒充模型推理成功。对旧冻结数据只做离线组装，不发新模型请求。独立审查和干净公开候选检查后，才考虑封存 AI 候选；公开 API、采集、A 控制器均保持运行。

实际解释是否改善必须另做有界自然验证；本轮前提检查和程序通过不能把旧失败升级为通过。新 ON 仍需完整 GO，包括固定目标、资源上限、唯一控制器、清理与临时周期还原。
