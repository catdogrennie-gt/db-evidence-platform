# 控制MySQL单次恢复尝试

延续STARTUP-01，仅增加可用隔离替身验证的执行编排，不接入正在运行的数据库或平台AI。相比直接重跑启动脚本，选择独立工程函数，复用既有纯判定器；不在这一轮扩展完整服务管理、自启动或冷启动。

私密状态目录由受信任部署适配器固定并限制访问。使用同目录固定文件的排他创建取得互斥；锁存在即返回忙，不按PID、文件年龄或租约自动抢锁。锁内重新获取新鲜观测；正确运行零动作，已有但未就绪仅等待。初次确认为缺失时，启动前再次观测，只有仍为合法缺失才将不可覆盖的意图记录落盘并最多调用一次固定启动能力。已有意图时不重复启动，保留记录供独立核查；不自动清空或新建另一个状态目录绕过。

观测和启动能力由可信私密适配器注入，必须遵守传入的剩余超时；函数本身不包含Shell、SQL、启动命令或任意程序接口，也没有公开路由/CLI。同步回调卡死无法由此函数强制终止，因此本轮只能证明有界回调下的编排，不能宣称已实现OS级超时。等待受单调时钟总预算和最多128次观测约束；启动异常/超时或结果不明都保留意图，不重试、不杀进程。状态只含原因码和尝试次数，无私密路径/原始异常。

验证健康无动作、并发互斥、检查间状态改变、配置/UUID/端口冲突、已存在启动中、启动异常、未就绪超时及旧意图阻止再次启动，所有启动均是测试替身。未来实际适配器仍需固定命令、进程身份、跨进程互斥和中断恢复验收；不得停止当前控制库来制造缺失。对应NFR-006/009、AT-017准备，非完整验收通过。

## 真实适配前提核查后的暂停决定

2026-11-13的隔离Windows实验确认普通父进程超时后子进程仍存活，子进程随后自然退出，无真实服务操作。当前编排的有界回调条件仍是前提，不能靠`subprocess.run(timeout=...)`直接满足。受控观测进程树与长期数据库监督必须分别设计：不能在固定启动回调返回时关闭可杀树Job而误停数据库。长期所有者、就绪/未知结果和句柄交接尚未实现，因此暂停真实执行适配，不扩展平台AI或注册自启动。该决定和重新准入条件见[STARTUP-01](../../validation/startup-01.md#2122续查实际执行适配暂停)；已通过的纯判定和替身编排不受此决定改写。
