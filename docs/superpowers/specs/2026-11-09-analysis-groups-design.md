# 官方监控接入与联合分析对象

## 目标与授权

本轮由用户明确提出并委托独立完成：使用官方 MySQL、Linux 主机模板采集真实数据，允许从 Zabbix 自由选择 host 和监控项，组成持续巡检的联合分析对象。之后可把应用与数据库组合为系统分析对象。无需等待用户在线确认，不播放提示音乐；本轮不涉及简历、邮件或公网部署。

用户希望看到的问题、图表与分析结果不因接入简化而缩水。接入应复用已有监控，分析应保留原平台的授权、问题、调查、冻结证据、人工处置和复验能力。

## 接入与数据

- 官方模板保持原样。真实 Linux 使用原生 Zabbix Agent 2；MySQL 使用官方 MySQL by Zabbix agent2。只在独立实验环境部署，旧主机、旧模板和历史报告保留。
- 锁链、SQL 摘要等官方模板不足的数据放入独立诊断扩展模板，清楚标注来源、单位与累计语义。摘要统计的 reset epoch 未知时不计算伪窗口差分。
- Zabbix 的 hostid/itemid 是来源内身份。保留监控项名称、key、tags、units、value_type、采样周期、状态和最后实际采样时间。未知 key 不等于不支持接入。
- 数值、字符、文本、日志和二进制必须区分。数值可以绘图，文本与日志可显示可用性和有限快照；二进制明确不参与数值分析。文本不能强制转数值，也不能未经字段授权和脱敏原样外发。
- 标签辅助筛选和说明，不证明因果、类型或资源身份。保留同名不同 host 的独立 itemid；不按显示名称合并曲线。

## 组合与权限

一个联合分析对象属于一个业务系统与一个 Zabbix 来源，可以选择多个已授权 host 的具体监控项。名称、说明及 host 间的可选依赖关系由用户登记。关系标记为人工登记，不标为自动探测事实。

组本身复用平台 Instance 授权和巡检资源身份；组内选中项是精确范围，不自动包含同一 host 的其他监控项。组中 host 不等同于多个 MySQL 实例，允许主机、数据库、探针或应用资料混合存在。后端根据值类型处理数据，已知 key 只用于额外语义增强，不能成为通用接入门槛。

来源地址与所属系统在已有绑定后仍不可重指向。编辑组会推进配置版本，旧任务通过既有 lease/fence 失效；已经生成的证据清单、图表和历史报告保持原样。停用组停止新采集和巡检，不删除历史。

## 页面流程

```text
监控对象 → 新建联合分析对象
  选择来源、业务名称
    → 选择 host，按名称 / key / 标签筛选具体监控项
    → 核对 N 个 host / M 个监控项及最近采样、单位、缺口
    → 可选登记依赖关系 → 保存
    → 查看数据 / 配置巡检 → 问题与风险 → 分析报告
```

对象卡片展示组成和实际新鲜度。数值指标看板保留来源 host、名称、单位、时间窗与缺口；文本和日志不伪装为折线。旧独立对象及原调查流程作为兼容入口保留。

## 分析与预算

巡检对联合对象读取所选项，保存冻结指标及证据。AI 可使用授权数值及经过约束的语义信息，不只接收旧固定指标白名单。模型继续输出事实、候选解释、反证、未知、下一步只读检查，每条事实引用实际证据；不能从同时变化断言根因。

查询与模型输入都有界。大窗口超出预算时应保留各序列的有界表示，明确截断或抽样方法、范围和缺口，不能因总点数刚超额把整组曲线抹掉。没有数据时保留缺口，不补零。真实模型验收采用有限次数与预算，外部调用失败不影响采集。

## 验收

1. 两个官方模板具有连续两轮真实新采样；记录支持、缺失和 unsupported，不能用 agent 本地自测冒充 Zabbix 历史。
2. 平台可发现官方监控项，名称、标签、单位和值类型与 Zabbix API 一致；未知 key 可选，所选项有稳定身份。
3. 创建、编辑、停用联合对象；至少覆盖一个 Linux host 和一个 MySQL host，组内同名项不合并，组外项不被采集或外发。
4. 对象出现在既有指标与巡检范围，数值曲线、非数值快照和数据缺口都可查看。
5. 一次后台周期分析读取本轮真实采样，保留任务、冻结引用和模型调用审计；没有异常时正常结果保留，不制造故障。
6. 越权来源/host/item、跨系统篡改、空或重复选择、失效项目、配置变更、同名曲线及预算边界具有针对性测试。原历史、原授权和原流程回归通过。

## 方案取舍

继续扩展固定 MySQL/host/probe 白名单无法覆盖应用与自定义项，故不采用。完全另起一套分析系统会重复授权与队列，故复用原平台 Instance、映射和巡检机制，把通用选择作为新主路径。首版为单来源联合对象；跨来源组合需要独立身份及授权设计，不在本轮偷渡。
