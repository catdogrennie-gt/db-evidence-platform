# 聚合分析产品收敛与结论优先报告

## 目的与授权

用户已明确授权本轮实施：保留 Zabbix 选择、聚合、数据查看，改善 AI 分析结论；删除旧自定义采集入口、单主机对象和无关旧页面，清理旧 Zabbix host。此前“不需等待、不要播放音乐”的委托继续有效。本文件记录实现决定，不另设等待批准环节。

产品目标是让内部运维人员打开结果就知道：发生了什么、为什么、现在该做什么。数据采集交给已有 Zabbix，平台负责按所选范围持续联合分析、解释与证据回查。

## 取舍

1. 仅重排旧 facts：改动少，但旧模型没有回答完整问题，不能满足需求。
2. **新增 AI 执行摘要，并精简产品页面（采用）**：新报告提供有依据的现象、原因、结论和操作；保留现有冻结证据、安全及调度基础。
3. 重写整个后端或另做仪表盘：迁移成本高，不能直接改善分析质量，本轮不做。

## 四个入口

| 入口 | 主要内容 |
| --- | --- |
| 问题分析 `/` | 当前问题、风险、巡检结果；进入结论优先报告 |
| Zabbix 接入 `/monitoring` | 来源连接、联合分析对象、按 host / item / tags 选择范围；没有单主机对象分区 |
| 数据查看 `/metrics` | 联合对象当前数据、类型化历史、来源和缺口 |

移除旧平台导航与创建页面。旧列表链接可以转到对应新入口；包含历史 ID 的证据、调查、事件等链接只能进入授权只读历史页或明确退役提示，不能伪装成当前数据。引用详情可以用抽屉或只读复用组件。保留身份认证、范围授权、敏感读取、审计、不可变清单和任务执行基础，不以删前端为由破坏历史引用。

## 报告顺序

```text
问题标题、对象、观察窗口、真实模型/规则与当前状态
┌ 结论摘要 ───────────────────────┐
│ 发生了什么：现象及影响范围                  │
│ 独立表层原因：各层观测与候选机制              │
│ 联合根因：支持的候选解释 / 证据不足 / 不适用    │
│ 问题结论：当前能确认什么、还不能确认什么       │
│ 建议操作：先检查什么，何时考虑人工变更及如何复验│
└──────────────────────────────┘
分析过程（按有用信息展示）
  关键事实、证据链、图表、关系、日志/文本、反证、未知
历史版本和审计（次要入口）
```

结论直接可读。图、拓扑和日志不是每次必选项，不显示空壳图或以全量曲线淹没结论。失败、待完成、过时、覆盖缺口保持明显；正常巡检不能冒充发现故障。

## 新 AI 报告契约

现有字段保留，新增 `executive_summary`。历史报告缺少此字段时明确说明“旧版未生成完整结论摘要”，保留原内容；不在读取时用规则拼接或补写历史 AI 输出。新 live prompt 版本必须生成该字段；rules_only 不伪造 live 摘要。

`executive_summary`：

- `headline`：不超过 100 字符的结论标题。
- `phenomenon`：Claim，说明发生了什么和现象。
- `surface_causes`：最多 3 个 Claim，区分各层表层机制或候选原因。
- `joint_root_cause`：Claim；有证据时为联合候选，证据不足或不适用是完整、有效的回答。
- `conclusion`：Claim，明确本次能作出的判断。
- `recommended_actions`：最多 4 个 Action。

Claim：`status` 为 `observed | supported_hypothesis | insufficient_evidence | not_applicable | refuted`；`statement` 1–500 字符；`evidence_ids` / `counterevidence_ids` 各最多 12 条；`unknowns` 最多 3 条。observed、supported_hypothesis、refuted 必须有引用；不足/不适用必须用文字说明限制。不存在“已证明根因”状态。字段严格拒绝未知键。所有嵌套引用必须属于本次授权冻结输入，不能引用未提供数据或其他对象。

Action：`kind` 为 `readonly_check | manual_change | observe`；`description` 1–300 字符；`evidence_ids` 最多 12；`risk` 为 `low | medium | high | unknown`；`requires_human_approval`；`prerequisites` / `verification` 各最多 3 条。manual_change 必须 requires_human_approval=true，并说明条件和复验。只给建议，不增加 SQL、Shell、发送邮件、写库或执行工具。风险标签不是操作授权。

prompt 要求先关注触发的问题、关键反证和来源时间，解释每层现象与联合原因之间的关系；相关不等于因果，恢复后的样本不证明整个历史窗口健康。端点、极值、累计量、采样缺口必须区分。执行摘要与事实不能互相矛盾；结构和引用校验不宣称语义完全正确。

实际核查发现模型会误读快照先后，因此输入额外提供确定性的 `snapshot_chronology`：只根据当前实际保留投影的时间与行数，隔离资源、来源及监控项，列出非空锚点与严格前后空样本的计数和引用。它不生成诊断、持续时间或恢复结论；裁剪后重新计算并纳入同一字节预算。异常优先选取完成后才按真实时间展示，不能因排序丢掉异常样本。

## 有界模型输入

新 live 报告每轮输入硬界从 12,000 升至 24,000 字节，同步调整初始裁剪额度，仍优先异常与反证、平衡保留各主机数值。保留 32,000 累计 token、调用次数、工具、费用及策略限制。输出硬界最多 3,000 tokens，仍尊重更低的显式 max_tokens。目标是为完整结论与所选数据留空间，不保证任意大窗口都完整入模；省略继续可见。旧报告的实际 12KB 记录保持原样。

## Zabbix 单一采集模式与旧数据

新配置 `collection_mode` 使用 `zabbix_only`（新部署默认）；`legacy` 仅作历史兼容/旧测试，不出现产品入口。Zabbix 模式拒绝新建直连草稿、连接测试、直连实例激活/重验/凭据轮换、自定义采集配置，以及旧单 host selection；组采集与源连接继续工作。历史读取、暂停/归档等管理仍按权限。后台不能继续调度非 monitoring 采集或旧单主机对象。worker 执行边界同样检查：切换前已入队/重试的直连任务、旧单 host Zabbix 任务也不得访问目标；测试用 transport spy 确认未执行，不能只验API/调度过滤。

本机旧三个 trapper host 是早期真实 Lab 数据，不能称造假。先备份控制库及 Zabbix 配置/历史，再精确删除旧 host，保留官方 Linux/MySQL、扩展模板和当前联合对象。平台旧实例归档、停用 mapping/schedules/policy scope，不级联删历史证据。只停能核实属于旧采集器的发送服务，不碰共享官方监控。运行凭据维护在仓库外完成，更新实际依赖配置并验证重连，不将秘密打印或发布。

## 验收

- 新 live 摘要结构、引用、动作权限与低预算/失败路径有回归；旧报告不变，rules_only 不冒充模型。
- 四个导航清晰；无旧单主机区、自定义模板入口与旧创建链接。旧历史 ID 不跳到当前观测。
- Zabbix 接入、联合选择、当前数据与冻结证据回查可用；敏感原文和跨部门拒绝仍有效。
- 实际新模型报告回答现象/原因/结论/操作，人工逐项核对关键数字、引用与未知；不能仅以 completed 当准确。
- 旧三 host 在线确已删除，官方采样仍推进，无旧发送器/采集任务在途；备份可查。
- 更新指南、README 实图和 CHECKPOINT。既有公开发布授权继续适用于经过检查的源码和版本。
