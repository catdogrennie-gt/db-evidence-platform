# 已采集诊断信息进入分析的可靠性修复

用户已授权持续按单问题演进；先修复真实失败，不开启第二个场景。

## 依据和范围

QUERY-FOUNDATION-01 的第一次自主调查在工具读取后触发上下文上限；第二次返回的 metric dimension 错用了 evidence UUID。实际冻结了配置、SQL 统计和日志，但初始投影的统一 9KB 小额配额让重复原始文本挤占了有用诊断。保持严格结构、权限、脱敏和冻结窗口；不把失败改为成功，不自动重标 finding。

## 设计

- 在已授权冻结证据中，以相同对象、来源身份、观察时刻的已验证结构化诊断替代重复原始文本；任意文本不据名称猜测或去重。
- 初始投影按来源分配容量，统计实际省略，不让前几项吞掉其他来源。有界行投影保留原计数和省略数量。
- 输入预算可显式配置，默认保持 24KB/32K；本机已补齐多源资料的配置使用 48KB/96K，硬上限 64KB/128K、最多 4 轮。费用和授权仍逐轮检查。
- 对可解析但结构不合格的最终报告，只允许一次无工具的重新输出，使用同一冻结授权上下文与静态字段错误路径，不修改模型的事实或发现。超限、引用无效、复修失败均保持失败。
- 修复后复测同一个真实场景，核查具体标题、现象、候选原因、证据、建议与恢复。A 保持维护，公开 B 不停服。

## 实施与检查

1. 增加去重、来源覆盖、严格纠错、预算与失败回归测试，先确认失败。
2. 修改 investigations/model_context，运行相关后台、上下文、权限测试；只读复现已有冻结报告输入，不重新造故障。

4. 有界单场景重测，保留失败；更新演示、操作手册及验收状态。每 30 分钟检查公网 B 和维护页 A。

## 复测暴露的准备性能缺口

v4.6 已在实际自主巡检中通过一次受限结构重试，形成有引用的延迟上升报告；后续任务排队后准备耗时，未在期限内完成。发现调查证据关联逐项 `get()`：51 条样本回归实测发出 51 次 SELECT，并逐项 autoflush。改为同一调查及授权冻结 ID 集合的一次现有引用查询，再批量添加关联。权限、窗口、清单上限和任务期限均保持；单独封存下一 worker 版本，不改已运行封存目录。等待时间与执行时间不能混为成功；仍需完整重测。
