# 单问题串行演进计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Complete one scenario before starting another.

**Goal:** 先用普通问题证明发现、分析、展示与恢复流程，再逐项增加需要多来源联合判断的场景。

**Architecture:** 沿用 Zabbix 只读取数、确定性检查、独立 AI 后台和 React 展示。故障只在登记的隔离目标复现，平台自主安排分析，验收脚本不提交答案或分析任务。

**Tech Stack:** Python / FastAPI / MySQL / Zabbix / DeepSeek / React / ECharts。

**Spec:** `2026-11-12-clear-problem-first.md` 与用户最新的单问题演进要求。FR-022～025 仍部分实现，真实场景验证补充 AT-013，不等于全部平台验收完成。

## 全局约束

- 同时只有一个待解决的场景；维护公网可用性和收尾发布属于保障工作，不另开场景。
- 每个场景先通过证据准备门槛：写明信息需求、要判断的现象、原因及排除项，核对实际接入、新鲜度、标签及单位语义、时间配对和权限；缺项先判断能否从 Zabbix 现有采集补入。再预演正常采样→自然发现→冻结分析→关闭→恢复及临时节奏还原，形成明确 `GO / SKIP` 后才允许 `ON`。关键前提不能满足时写明缺项并标 `SKIP`，不能先制造问题再长时间盲等。
- 每 30 分钟复盘目标、实际结果、阻碍、计划与执行偏差；记录下一动作。不能用新增页面或报告数量代替成功分析。
- 同时检查公开演示可用性：B 首页与当前静态资源、访客只读登录、问题列表与实际报告；A 撤下期间应为维护提示且公网写请求拒绝。保留实际失败，不将预期撤回的旧故障地址当作在线站点。页面 HTTP/接口检查不冒充浏览器视觉验收；发现故障先恢复可用性。
- 单场景原则限时 60 分钟。30 分钟节点判断继续、缩小问题或跳过；到时仍无可验证结果则保存失败和下一步，换下一项。延长需有明确、接近完成的依据，不无限调整提示词。
- 有报告不等于通过；未知根因如实保留，不能虚构具体 SQL、泄漏、执行计划或持续时长。
- 公开 A 保持撤下，直到至少一个场景的发现、解释、恢复和展示均验收通过。将来公开页只显示通过的场景，开发目录留内部。
- 外部 B 持续可用；候选封存、检查、提前 1 分钟通知后切换，失败回退。禁止直接覆盖运行源码或并行启动第二个故障控制器。
