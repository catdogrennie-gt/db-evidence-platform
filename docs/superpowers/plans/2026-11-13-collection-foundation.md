# 数据采集基础补齐实施计划

**Goal:** 先让数据库、所在主机和应用的必要信息真实可读，再继续逐项验证诊断能力。

**Architecture:** 复用 Zabbix 官方 Linux/MySQL Agent2 模板。配置、性能视图和有界日志查询通过 Agent2 的固定 SQL 文件扩展，平台仍用只读 Zabbix API；AI 不连接数据库。Prometheus/mysqld_exporter 可补充指标，不能代替日志通道，暂不重复部署同一指标链路。

**Spec:** 用户 2026-11-13 最新采集优先要求；`docs/platform/01-requirements.md`、`02-architecture.md`。已有授权持续执行，由当前会话完成，无需重复选择执行方式。

## 约束与验收

- 不停公开 B；新前端封存并切换网关，旧资源保留。自动刷新仍默认关闭。
- 仅读已登记实验资产；固定 SELECT、行数和超时限制，不将所有变量、SQL 字面值、凭据送给模型。
- 数据为空、日志未开启、权限不足、失效采样分别记录；新增数据不补写旧报告。
- 每 30 分钟检查计划方向、采集实际结果和公开演示可用性。采集不足先补采集，不开启故障等待材料出现。
- 风险重点：同一主机多数据库不可重复算多台物理机；采样时间不是读取时间；累计计数不当速率；日志空不能证明完整时间窗无错；32 项选择限制通过诊断包控制体量，不无界扩容 AI 输入。

## 选择组件依据

- [Zabbix 7.0 MySQL 插件](https://github.com/zabbix/zabbix/blob/release/7.0/src/go/plugins/mysql/README.md) 支持命名连接与固定自定义 SQL。
- [mysqld_exporter](https://github.com/prometheus/mysqld_exporter) 提供指标采集；不把指标 exporter 当日志存储。
- [Alloy 文件日志](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.file/) 可作为后续大规模日志通道；只有需要全文增量检索时再引入 Loki，当前先验证 Zabbix 有界诊断接入。
