# 先交付清楚的问题分析

用户最新调整：先易后难，允许先验证 Zabbix 本身也能告警的明显问题。首要目标是一份真实、清楚、可直接演示的成功分析，而不是继续扩大复杂场景清单。

## 产品判断

- 指标偏离基线只是变化线索，不自动等于故障。变化线索与已支持的问题分开展示，不计入问题数量。
- 问题标题写具体问题；报告最上面说明发生什么、原因依据、结论和建议。具体根因未知时保留限制，但不能因此否认已经观察到的问题。
- 正常巡检保留在折叠的巡检记录中；保留历史报告和失败记录，不改写旧报告。
- AI 对现有线索的提请复核必须通过现有引用、维度、授权校验，且对应当前报告和同一变化周期。仅报告标题或空 findings 不构成问题登记。

## 首个简单场景

隔离实验 MySQL 固定增加最多 25 个只读空闲连接。容量 40，预检必须保留至少 6 个连接位置，不修改上限、不制造完全拒绝连接。B 通过原有 Zabbix 数据接入一个小型连接分析对象；AI 看实际连接数、容量、可用性等事实，不接收预设答案。A 继续共享互斥故障控制器，重复打开不叠加，关闭清理。

## 执行与验收

1. 后端增加问题/线索/历史的投影与对应测试，不改原始事件和报告语义。
2. 前端将线索、正常巡检折叠；具体原因在摘要首屏直接显示。用户最新要求：默认关闭自动刷新，不继续扩展局部刷新；通过手动刷新查看新结果。
3. 完成 typed manifest 引用参数修复，保留权限及冻结窗口约束。
4. 使用不可变候选和可回退切换更新服务，持续检测两个新站和两个原站。
5. 新场景真实开启 → B 自行检查并分析 → 核对实际调用、标题、数值、建议 → 关闭并核对新鲜恢复数据。任务完成不等于诊断通过。
6. 成功后更新演示入口和操作手册，再按同样闭环增加问题；复杂失败场景保留为待完善。

## 普通问题优先与容量事实（追加）

真实连接测试中，AI 读取到了连接数 34、容量 40，却把未达到硬上限解释为无需处理，未识别余量风险。保留该失败报告，不改写成成功。先用最基础的锁等待等明确问题展示完整链路；复杂联合场景后续迭代。

容量判断采用可复用的显式规则：从 Zabbix 已选择的同主机数值项中，用 `sl.capacity.group`、`sl.capacity.role=used|limit` 配对，在 limit 项配置 `sl.capacity.warning_pct`。平台核验同来源、配置、采样语义、新鲜度与时间对齐；连续三个配对样本超过配置水位才形成容量风险。规则提供用量、容量、占比、余量和两个原始引用，AI 解释候选原因和人工建议，不将低活跃度或未到硬上限当作风险消失。缺样本不视为恢复，规则不证明宕机或具体根因。

发布约定：切换前通知用户“1 分钟后切换”，到时通过健康检查后直接切换，失败回退；不反复等待确认。保留外部演示服务、旧静态资源及可回退目标。
