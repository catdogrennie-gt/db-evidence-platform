# Zabbix 自动巡检与故障研判操作指南

**当前状态：2026-11-09 本轮联合对象限定验收已完成。** 官方采集、11 项 HTTP、对象 / 向导页面、权限与冻结保护，以及正常与受控锁后台周期均已有实际结果。锁线程 / 事务与冻结引用匹配，CPU 范围误读明确保留。后端 571 通过、10 跳过、6 子检查通过，前端 27 项及最终类型 / 构建检查通过。详细范围见[本轮验收](acceptance-analysis-groups.md)，快速步骤见[联合对象上手](analysis-groups-guide.md)。[2026-11-08 旧版记录](acceptance-zabbix.md)与[历史 Release](releases/legacy-platform-2026.11.08.md)单独保留。

日常从“问题与风险”开始：查看自动巡检结果，打开报告，沿证据关系与曲线核对问题，再进入已有人工处置和复验流程。完成来源及巡检策略配置后，不要求每天先选择一个历史时间窗才能获得结果。

## 首次接入：由维护者配置 Zabbix

### 1. 登记只读来源

打开“监控对象”，点击“连接 Zabbix 来源”，填写名称、Zabbix API 地址、归属系统、只读 API Token 及需要限定的主机组 ID。保存并验证连接；口令和 Token 的实际值只在部署环境内提供，不放在本文或截图中。

验证成功后应核对来源状态、可见主机和最近成功时间。服务端保存凭据，界面仅显示是否配置，不会返回旧 Token。Token 轮换沿用原来源；已有对象映射后，不把来源地址改指另一个 Zabbix，应登记新来源。

连接成功不等于所有类别都有数据。必须继续检查选定对象的指标、锁快照、SQL 摘要、日志等实际能力。

### 2. 创建联合分析对象

在“监控对象”点击“新建联合分析对象”，按四步完成：

1. **定义范围**：选择一个已连接来源，填写名称和分析目标；组继承来源所属业务系统。设置数据采集周期和保存后是否启用，分析周期稍后在巡检策略中配置。
2. **选择数据**：选一个或多个允许的 host，按监控项名称 / key、主机标签或 item 标签查询。标签支持等于、包含和存在筛选，分页查询不清空已选项。勾选 1–32 个具体 items，逐项核对来源 host、单位、值类型、状态与最近实际采样。
3. **登记关系**：可选登记已选主机之间的运行、依赖、连接或关联关系，最多 32 条；均标记为人工登记，不是自动发现的因果事实。
4. **核对保存**：检查主机数、项目数、非数值项及缺口后保存。从对象卡片进入“查看数据”或“配置巡检”。

一个组限定一个来源和一个业务系统，只包含精确选中的 items，不自动纳入 host 上的其他监控项。未知 key 可选，同名但不同 host / itemid 的项目保持独立；标签用于筛选和说明，不证明资源类型或因果。此路径通过 Zabbix 读取已有数据，不要求目标数据库口令，也不将 hostid 当作 MySQL UUID。

编辑或暂停使用卡片上的“编辑范围”“暂停 / 启用”。来源与系统归属不能在组建立后改指；需不同来源时新建对象。配置变更推进版本，旧在途任务不能覆盖新配置，已有报告及冻结证据不改写；暂停后停止新采集与相关巡检，保留历史。

原“选择已有对象”的单 host 映射保留为兼容入口，不限制新的多 host 联合对象。更完整的类型、权限与例子见[联合对象指南](analysis-groups-guide.md)。

### 3. 核对能力与新鲜度

| 能力状态 | 应如何理解 |
| --- | --- |
| 可用 `available` | 当前映射有相应能力，仍需核对所选窗口内是否有有效样本 |
| 缺失 `missing` | 没有需要的 item 或观测，保留为未知 |
| 不支持 `unsupported` | 当前来源或模板不提供此类资料 |
| 过期 `stale` | 曾有观测，但不足以代表当前情况 |
| 失败 `failed` | 本次读取失败，查看原因后处理 |

官方模板保持原样，Linux 使用原生 Zabbix Agent 2，MySQL 使用官方 MySQL by Zabbix agent2；锁 / SQL 等额外资料由单独诊断扩展提供。平台读取已有监控，不会因保存联合对象而自动安装 Agent 或修改模板。模板名称不能证明所有监控项已成功采集，尚未满足较长基线的计算项仍可为 unsupported。

通用数值项不要求命中固定 key 白名单；已知 key 仅用于额外语义增强，不把未知项猜成锁、SQL 或日志。数值可以绘图，文本 / 日志以有限历史单列，二进制不参与数值分析。读取文本 / 日志原文需要该组范围的 `evidence.read_sensitive`；没有权限不等于没有采集，拥有原文读取权也不自动允许对模型外发。

曲线保留原始时间、单位、覆盖与截断状态，缺失值不补零。官方模板可能按“值变化 / 心跳”稀疏保留 history；短窗无新记录不能直接等同采集失败，也不能把旧值补写成当前值。应核对保留语义、心跳、最近实际样本及覆盖原因。组卡片的最近观察不代表每个所选 item 都新鲜或健康。

### 4. 启用巡检策略

策略需要明确负责人和授权对象。先选择分析模式、轻量信号检查周期、综合模型巡检周期、异常紧急通道、冷却时间与每日运行预算，再启用。

| 设置 | 当前默认与含义 |
| --- | --- |
| 轻量信号检查 | 默认 300 秒，定期检查已有数据中的异常信号 |
| 综合巡检周期 | 默认 1800 秒；没有阈值异常也会按周期检查。`rules_only` 不调用模型，`live_redacted` 还须满足模型与外发条件 |
| 异常紧急通道 | 新问题或实质变化时提早安排分析，仍受冷却、范围、队列与预算约束 |
| 分析模式 | 规则结果与真实模型输出分开标识；模型未配置不能显示为实时 AI 已成功 |
| 外发确认 | 只有明确允许的脱敏来源可送往模型，策略保存不替代既有系统 / 实例授权 |
| 每日运行预算 | 限制自动综合调查次数，不是实际账单金额，也不承诺固定响应时间 |

页面应能查看最近完成、下一次到期与停止原因。负责人撤权、策略停用、缺少外发确认、来源离线、队列限制或预算耗尽时，不会靠扩大权限继续分析。电脑休眠或服务重启后的过期周期不应全部补跑成调用风暴。

一个策略可覆盖多个对象；联合组在原有授权与调度中是一个资源，不把组内 host 个数当作数据库实例数。组采集默认每 60 秒，可设置 30–3600 秒，与综合分析周期独立。单次调查最多五个资源、每位用户最多三个在途调查，较大范围分组调度。手动运行是维护 / 测试入口，不是日常使用的必要步骤。

`rules_only` 由确定性代码生成规则与覆盖结果，不调用外部模型。`live_redacted` 才会请求真实模型，并检查当前权限、外发许可、冻结引用和预算。通用数值及受约束的名称、单位和语义标签可用于分析；自由说明保留在本地，不外发。文本 / 日志原文、任意 item 参数和不安全元数据不会直接发给模型。模型失败不应阻断独立采集。

## 日常调查：从一个问题读到证据

### 1. 先看结果与覆盖

“问题与风险”区分当前已观察到的问题与带条件的风险。先看严重程度、对象、首次发现 / 更新时间、分析模式及覆盖状态，再进入详情。正常的周期巡检留在巡检历史，不为了展示数量制造告警。

风险需要列出观察窗口、确定性计算、阈值和假设。样本不足或趋势断档时不能给出精确预测；模型提出的风险也不自动成为已证明的事实。

重复发现同一问题应关联同一事件，追加报告版本；不同 SQL 摘要或不同资源的问题不会仅因模型标题相似就合并。

### 2. 读报告摘要与证据关系

打开问题后，先看报告是否完成。排队中、运行中、失败或无报告都不能显示成已完成诊断。完成报告应能追到证据引用、曲线、反证、未知与下一步检查。

关系图中需要分清四种信息：

| 类型 | 含义 |
| --- | --- |
| 已观测 | 有实际快照、指标或记录支持的观察关系 |
| 已登记 | 由配置或映射登记的依赖，带来源说明 |
| 候选解释 | 模型或调查者提出、仍需验证的假设 |
| 条件预测 | 在明确计算与假设下的风险判断 |

点击节点及关系的证据入口，核对同一对象、同一窗口与原始含义。连线顺序、同时上升的曲线或模型措辞都不自动证明因果。界面不使用未经校准的“根因置信百分比”。

### 3. 对照冻结曲线与当前指标

问题报告的图和曲线使用该版本的冻结数据。检查窗口、单位、采样、聚合、反常点与缺口；返回旧报告时，上游后来产生的新数据不会替换原图。

本轮按序列分配点数 / 字节预算，保留有界表示并说明抽样、截断或省略。正常周期为 18 条冻结曲线、17 条数值入模、1 条明确省略；受控锁周期为 18 条冻结、13 条数值入模、5 条明确省略，另有一条非空锁边。不能将冻结曲线数等同模型实际读取数。2026-11-08 图示锁报告曾整组省略曲线，历史缺口继续保留，不会被新实现补写。

需要了解现在的情况，再进入明确标识的“当前指标”下钻，选择对象和时间范围。当前指标用于新的观察，不能作为旧报告当时已经掌握的证据；重新分析会生成另一份不可变报告版本。

同样要检查数值语义：探针耗时可能包含连接、认证与 SQL，不等于纯网络 RTT；SQL 摘要可能是累计统计，不能把生命周期最大值当窗口最大值。缺单位、基线或有效差分时，结论应保留未知。

从巡检历史打开完成报告 `46fd02bd…`，按以下顺序核对：

1. 触发方式为后台 `periodic`；冻结窗口为 **2026-11-09 04:49:29–05:49:29 UTC**，包含 **05:49:17 UTC** 的实际锁快照。

4. 报告有 4 条 facts、2 条 hypotheses、3 条 unknowns 和 1 条待核验 finding。**第 4 条 CPU 事实把首值 3.358 当作范围下界约 3.4；实际最小值 2.7538、最大值 4.53549。** 引用可回读不证明区间解释正确，原输出继续保留。

6. 查看独立实验清理结果：负载工作进程结束、事务回滚、残留实验会话 / 锁为零，数据集及前后校验均通过。这是受控实验清理，不能读成平台自动处置成功。

提示已补充首末端点与窗口极值的区别，仍需核对模型的数值解释；待核验 finding 不代表已由用户签署确认。完整时间与边界见[受控锁验收](acceptance-analysis-groups.md#受控锁联合案例)。

从联合对象的巡检历史打开完成报告 `024d…`，核对以下几处：

1. 触发方式为后台 `periodic`，分析组成包含两个 host 和一条人工登记关系。

### 历史记录走读：一次自动周期锁分析（2026-11-08）

无需现场重新注入故障或调用模型，可从“巡检设置”的最近运行进入已完成调查 `0f3f66b6…`：

1. 核对它的触发方式为后台 `periodic`，而不是人工运行；分析范围包含数据库、主机与连接探针。
2. 查看冻结窗口截止 **2026-11-08 15:19:11.474 UTC**，确认它覆盖 **15:19:05 UTC** 的实际锁观察。
3. 沿报告引用对照原始锁快照：事务 `1864` / 线程 `14485` 阻塞事务 `1868` / 线程 `14524`，核对编号和方向，不只读自然语言摘要。
4. 查看 2 次真实 DeepSeek 与 2 次只读工具调用，以及事实、候选解释、未知和显式待核验 finding；运行成功不把候选解释变成业务根因。
5. 若要了解现在的情况，再进入当前指标，或查看独立 Lab 的后续恢复 / 清理记录；这些新资料不改写旧报告，也不表示平台自动恢复数据库。

更早的引用失败和窗口早于异常的调查仍保留，不能拿它们当作本次成功报告。详细核对范围见[实际验收](acceptance-zabbix.md)。

### 4. 转入人工处置与复验

从问题进入原有事件、调查或处置记录，核对授权范围与证据，明确计划和实际外部操作，再使用后续有效样本复验。AI 只提出解释与下一步只读检查，不执行 SQL、Shell、变更或邮件发送。

复验结果中的 `improved`、`not_improved`、`inconclusive` 必须按实际证据解释。连接检查成功不证明锁等待消失，模型写“已恢复”也不替代确定性复验。人工备注与报告原文分别保存，后续知识条目继续继承来源权限。

## 遇到这些状态时

| 现象 | 下一步 |
| --- | --- |
| 来源可连接，但对象或曲线为空 | 检查只读主机组、对象选择、映射能力、时间范围及 history 保留；不使用演示数据填空 |
| 有数据库指标，却没有锁 / SQL / 日志 | 查看能力说明与 item 映射，按真实缺口继续调查，不根据模板名称推断存在 |
| 对象数量比维护者看到的少 | 核对业务范围与读取权限；管理权限与资料权限不同 |
| 来源过期、离线或读取失败 | 查看原因、最近有效观察与巡检状态；失败不等于目标宕机，旧值也不代表当前健康 |
| 模型未运行或失败 | 核对模式、负责人权限、外发确认、预算和队列；保留失败，继续查看规则与已有证据 |
| 旧报告与当前指标不同 | 核对各自窗口与报告版本，旧报告读取冻结资料，当前看板读取新历史 |
| 取消选择后仍有历史 | 历史保留是预期行为，未来巡检暂停；访问历史仍需当前权限 |
| item 可选但 key 未识别 | 按名称、单位和值类型核对语义；未知 key 可作通用观察，不能自动当作专用 MySQL 诊断资料 |
| 文本 / 日志原文无法打开 | 核对组范围的敏感证据读取权限；这与没有数据是不同状态 |
| 短窗无 history 但 item 正常 | 核对“值变化 / 心跳”稀疏保留和实际 lastclock，不能补旧值或直接判故障 |
