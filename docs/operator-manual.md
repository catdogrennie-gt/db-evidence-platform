# 操作手册

这套平台把 Zabbix 已有的数据放在一起，持续检查数据库与关联应用的状态。日常先看问题结论，需要核实时再看曲线和证据；处理建议由人判断和实施，AI 不执行 SQL、Shell 或数据库变更。

本手册随功能维护。**页面实现、实验负载实现、平台实际发现并正确解释，是三个不同的完成状态。** 新场景是否验证通过，以[场景验证清单](validation-scenarios.md)及其实际记录为准；本手册中的启动示例不是“任意机器部署已经通过”的承诺。

## 1. 先选入口和身份

| 入口或身份 | 可以做什么 |
| --- | --- |
| B 完整平台：演示只读访客 | 查看授权演示业务的对象、指标、问题、报告、来源摘要、巡检与配置状态；不能保存配置或触发任务 |
| B 完整平台：运维维护者 | 在授权业务范围内连接来源、组合数据、配置巡检和阅读结果；管理权限与数据权限分别授予 |
| A 快速演示与故障验证工具 | 公开仅展示已验连接水位场景；其他候选限内部准备与验证 |

当前公网入口和演示账号见[README](../README.md#在线体验)。新安装使用本机单独生成的账号，不能把公开演示口令作为自己的管理员密码。

B 的四个主要页面：**问题分析 → Zabbix 接入 → 数据查看 → 配置**。顶部业务筛选与时间范围影响当前查看，**不会自动改写后台巡检策略**。只读用户看到“可查看，不可操作”是正常状态；只读不表示只能看首页，凭据和内部连接地址仍不公开。

## 2. 首次接入 Zabbix

这一步由具备来源管理和相应业务授权的人操作；访客可以跳到第 5 节。

1. 先在 Zabbix 配好实际数据库、服务器和应用采集，检查最新样本。数据库和主机优先沿用官方模板，模板不足的诊断信息仍经 Zabbix 扩展采集。
2. 在 Zabbix 创建独立只读身份及 API Token，只开放需要分析的主机组。不要提供 Zabbix 管理员凭据或业务数据库口令给平台。
3. B 打开 **Zabbix 接入**，选择 **连接只读 Zabbix**，填写来源名称、API 地址、所属业务系统、只读 Token 与允许主机组。
4. 保存后核对来源状态、可见主机和最近成功时间。连通只证明 API 可访问，不能证明 SQL、日志或每项诊断信息都已经采到。

已有对象的来源不要改指另一套 Zabbix；不同来源另建。平台不会自动安装 Agent、创建数据库账号或改上游模板。采集准备参见[官方模板与扩展说明](zabbix-official-setup.md)。

## 3. 勾选数据，组成联合分析对象

在 **Zabbix 接入 → 新建联合分析对象** 按向导操作：

| 步骤 | 怎么填写、怎么核对 |
| --- | --- |
| 定义范围 | 选择一个 Zabbix 来源，写清业务名称和分析目标，设置平台取数周期 |
| 选择数据 | 按主机、监控项名称/key、主机标签或监控项标签过滤，勾选需要一起分析的具体项目 |
| 登记关系 | 可选登记“应用连接数据库”“数据库运行于主机”等关系，帮助理解对象；登记关系不是已证明的因果 |
| 核对保存 | 核对主机、1–32 个监控项、单位、值类型和采样状态，点击 **保存联合对象** |

一个联合对象来自同一 Zabbix 来源和业务系统；只包含勾选项，不自动加入主机上的所有数据。筛选和翻页保留已选内容。未知 key 也可选择，不用先把数据强行归类成平台预设的数据库类型。

建议围绕问题选数据，而非把所有指标塞满：应用请求耗时、数据库调用耗时、连接池/排队，配合数据库连接余量、SQL 代价、主机资源和必要诊断信息。数值能绘图；文本与日志保留原含义，访问原文仍需敏感读取授权。

保存后先点 **查看数据**：核对 **数值图表**、**原始历史 / 文本与日志**、**组成与登记关系**，确认时间、单位和数据缺口，再配置巡检。没有采样的项可以保存等待采集，但不能当成正常值。

### 3.1 先把诊断材料接齐

数据库与主机优先使用官方模板；配置、性能视图及慢/错误日志用固定只读诊断包补充，应用有实际日志时一起选入。只读访客可看脱敏诊断字段，原文权限独立控制。具体内容、接入步骤与缺口见[诊断数据准备与核对](collection-foundation.md)。首页默认最近 7 天，自动刷新默认关闭；这不会修改后台调查窗口或补出新增数据的历史。

## 4. 配置自主巡检

维护者进入 **配置 → 巡检**，选择需要持续检查的联合对象，设置模式、周期和模型预算，保存并启用。

- **确定性规则**：只做程序检查，不调用外部模型。
- **脱敏 AI 综合分析**：需要模型配置、业务数据权限和明确外发授权；模型关联当次获准证据，提出解释和建议。
- **检查周期**与**综合巡检周期**不同；平台取数周期还与 Zabbix 上游采样周期不同。上游没有新样本，提高平台频率也不会生成新数据。
- 后台按策略运行，不要求网页常开。周期综合分析不以“Zabbix 已发告警”为唯一前提。

指标变化筛查会保留首次有效稳定采样作为对照，按来源、监控项及配置版本隔离。它只是实测参考，不等于健康基线；没有合格参考时不强行判断。业务长期改变后，由维护者确认并刷新联合对象配置，等待新参考形成。不要反复改配置来消除真实异常，历史证据和报告仍需核对。

启用后核对最近检查、下一次计划、实际任务状态和最近完成时间。没有新报告时先查来源、策略、队列、权限、外发许可和预算，不能用反复点主动分析代替检查调度问题。**规则或模型发现的线索不等于根因已确认。**

### 可选：容量水位检查

需要明确关注资源余量时，在 Zabbix 为两个数值项配置以下标签，然后把它们同时选入联合对象。平台从最新采集的标签读取规则，不根据监控项名字猜测容量，也不修改 Zabbix 模板。

| 标签 | 用量项 | 容量项 |
| --- | --- | --- |
| `sl.capacity.group` | 同一组名称，如 `mysql_connections` | 相同名称 |
| `sl.capacity.role` | `used` | `limit` |
| `sl.capacity.warning_pct` | 不填 | 关注水位，如 `80` |
| `semantics` | `gauge` | `gauge` |

两项须来自同一主机、单位相同，并有已核验周期的持续采样。连续三组新鲜、时间对齐的样本达到关注水位后，平台登记容量风险，显示用量、容量、占用比例和剩余额度；AI 再解释候选原因和建议。尚未达到硬上限不代表余量充足；低活跃度也不能否定连接额度风险。缺失、过期或无效样本不视为恢复。只有连续三组后续有效样本回到关注水位以下，才标记该项风险恢复，不据此宣称整体健康。

## 5. 日常读问题与证据

进入 **问题分析**，先核对业务范围、巡检状态和覆盖缺口，打开需要关注的问题：

1. 先读摘要：**发生了什么 → 直接原因/关联原因 → 当前结论 → 建议怎么做**。
2. 核对它是实际观察、规则线索还是 AI 待核验解释。信息不足、无法确认和被反证都应保留，不能只看模型语气是否肯定。
3. 需要时展开分析过程，查看引用的数值、趋势图、登记关系、支持/反对依据以及缺少的信息；并非每份报告都必须有拓扑图或联合根因。
4. 核对报告的对象、时间窗和来源。旧报告保留当时证据，不会随着现在的数据自动改变；跳到 **数据查看** 查询的是所选新窗口。
5. 由人员决定是否处理，再用后续实际采样核验。模型写了“恢复”或任务显示 completed，都不能代替恢复证据。

### 冻结规则事实、AI 解释与当前状态

版本 08 的 API 与静态资源已上线，以下展示已通过程序、真实历史只读回放及公开 HTTP 核验；原图表资源继续可读，访客写入仍拒绝。采集和 AI 后台没有重启。**浏览器视觉验收因工具连接超时暂不可验证，不能据此标为页面视觉通过。**

| 内容 | 阅读方式 |
| --- | --- |
| 冻结规则事实 | 在问题详情或历史报告中，先看报告窗口内由原始采样重新核验的用量、容量、比例、余量及配置水位；可展开三组配对观测和两条原始引用 |
| AI 分析 / AI 判断 | 查看模型原本的解释、候选原因、建议和未知；它不会改写已核实的规则事实，也不等于已确认具体根因 |
| 当前观测 | 查看后续样本是否恢复；当前值与历史报告窗口分开，不用当前恢复覆盖过去风险 |

真实历史回放中，报告窗口仍为 **33/40、82.5%、剩余 7、配置水位 80%**，当前采样则为 **8/40**。两份历史任务各有三组配对和两条有效引用；其中一份模型分析失败，仍能显示独立规则事实。这次回放没有开启故障、提交 AI 任务或修改旧报告。早期报告缺少合格冻结依据、数据无效或不可见时，事实区可能为空，不能把空白当成健康。

首页将结果分成三类：**当前问题/潜在风险**需要有规则或经引用核验的问题依据；单纯数值升降放在折叠的**变化线索**中；已回落或配置变化的记录放在**历史观测**。正常巡检也会留报告，放在折叠的**巡检记录**中，不计为问题。报告最上面先读具体标题、结论、现象、原因说明和建议，下面再展开证据。报告窗口之后出现新采样时，会标明旧报告的时间限制，不能将旧判断当作最新状态。

实际规则确认过且后续已有恢复观测的问题，最多三个直接显示在**最近已恢复的问题**中，保留报告入口；它们不计入当前问题数。普通基线回落和未核验的 AI 假设仍放在历史观测中。

有数据而没有 Zabbix 告警，可能是尚未满足当前阈值，也可能需要关联多个指标。验证新增发现时要同时核对**当时的模板、宏、触发器和实际事件**；不能为了证明平台价值而关闭 Zabbix 告警。若上游已有告警，本次价值应记为补充解释，而非新增发现。

## 6. 内部故障验证工具

**公开故障触发页已撤下，以下仅供维护者在内部验证环境使用。** B 完整平台继续提供只读查看。开发中、未跑通或解释不足的场景不对访客开放；将来只有发现、分析、恢复及展示均验收通过的场景才进入公开演示，可以先从基础问题开始。内部仍保留失败记录和待优化场景。

打开 A 后先看场景目录的状态。**实现待完整验证**表示负载代码可用，尚不等于平台已正确发现并解释；**尚未实现**的场景不能启动。复杂场景的发现、解释和恢复按项验收，不能因任务完成就标记诊断通过。演进先验证容易观察的明确问题，再逐步增加联合分析难度；Zabbix 已能告警的问题也可以用于验证解释能力，但不能声称是平台额外发现。具体状态以页面和验证清单为准。

页面**默认关闭自动刷新**。点击 **刷新数据** 才读取最新结果；后台取数和巡检仍照常进行。B 顶部也默认关闭自动刷新，需要时可自行开启。刷新网页数据不会加速上游采样，也不会发起一次 AI。

先读每项的**业务表现 → 本次Zabbix告警对照 → 平台发现线索**。没有对应告警，可能是尚未达到实际阈值、缺少联动规则，也可能是采集失效；这三种情况不能混写。上游已有告警时，本平台展示的是额外的关联解释。预设说明是验证背景，真实结果以当轮报告和引用为准。标为“发现与恢复已验证 · 分析待完善”的场景，仅表示发现与恢复已验证，不能当成根因诊断验收；下方“上次人工核对的实测”属于历史验证记录，不是当前实时值。

1. 选一个可用场景，点击 **开启问题**。内部维护者共享同一开关，同一时刻最多一个场景生效，重复开启不叠加负载。
2. 看 **平台正在做什么** 中的实际取数周期、检查周期、最近检查与任务状态。A 会临时申请加快 B 的检查，界面刷新不等于重新调用一次 AI。
3. 看 **发现与分析** 及 **当前监控 · 实际采样**，必要时进入 B 阅读完整报告。A 不创建调查、不调用模型，也不把预期答案交给 B。
4. 点击 **关闭问题**，先确认负载控制状态，再等待后续实际样本恢复。关闭网页不会主动关闭实验；控制服务失联后由短租约停止负载。
5. 目录切换只改变本页查看，不会自动切换共享故障。要换一个问题，先关闭当前故障，再选择并开启新场景。若仍显示正在释放、不可用或错误，先核对清理结果，不通过增加连接或重复发任务强行推进。

**开关与所看场景分别显示。** 只有当前查看的场景确实运行时，按钮才呈绿色；其他场景显示“此场景未运行”。运行期间的关闭按钮会写明真正要停止的场景名称，不会因为切换目录而同时开启多个问题。状态待确认时，页面保留未知提示。

开关没有次数、冷却或“必须等待监控确认恢复才能再次打开”的操作门槛。模型调用仍遵守平台自己的预算和去重策略。**负载已关闭、数据库直接清理完成、Zabbix 已采到恢复、旧报告内容，分别看待。**

## 7. 遇到空白、未知或失败

| 看到的情况 | 先检查什么 |
| --- | --- |
| 来源连通但没有数据 | 允许主机组、选中的具体项、窗口、history 保存与 item 是否 unsupported |
| 图表没有新点 | 上游采样/心跳、实际采样时间和缺口；不能补零或用旧值伪装当前正常 |
| 有数据库数据但没有应用信息 | 是否已经在 Zabbix 采应用并选入同一对象；平台不会凭空补出应用指标 |
| 页面显示当前没有问题 | 最近是否真的完成有效巡检，是否有覆盖缺口；没有结果不等于健康 |
| AI 排队、失败或未运行 | 模式、授权、模型可用性、预算和后台 worker；保留失败，不用规则冒充新 AI 报告 |
| 报告是历史结果 | 对照报告冻结窗口和当前观察，不把上次完成时间当成本轮完成 |
| 问题再次出现却显示旧报告 | 核对报告冻结终点是否覆盖本次变化；目前尚有阶段复用缺口，旧报告不能代替本轮结论 |
| A 显示连接中断或状态过期 | 先查服务和最近成功接收时间；连接断开不是数据库恢复的证据 |
| 访客不能查看某部分 | 核对业务范围和只读投影；原文、凭据或非演示业务仍可能被限制 |
| 保存操作报版本冲突 | 重新读取最新配置，不覆盖其他人的范围或策略修改 |

## 8. 维护者启动与恢复

以下是**已经初始化好独立控制库和私密配置后**的源码约定示例。首次安装、建库、迁移与账号生成按[部署说明](platform/07-operations.md)进行；不要用初始化命令覆盖已有环境。

在对应后端版本目录、使用该版本依赖环境，分别启动 API、取数 worker 和 AI worker：

```powershell
$env:DBA_PLATFORM_CONFIG='D:\Private\DBEvidence\config.json'
python -m uvicorn platform_app.api:create_app --factory --host 127.0.0.1 --port 18480 --no-access-log
```

```powershell
python -m platform_app.worker --config D:\Private\DBEvidence\config.json
python -m platform_app.ai_worker --config D:\Private\DBEvidence\config.json
```

API 与两个 worker 是独立进程，上述前台命令分别在终端/受控服务管理器中运行。私密配置的端口、schema 和运行目录必须匹配此环境。恢复时先核对 VM、Zabbix、控制 MySQL 和 API ready，再查后台心跳；不要重建数据目录或直接按一个旧 PID 杀进程。

A 的多场景站在单独的 Lab 版本目录使用 `SCENARIO_SITE_CONFIG` 指向仓库外配置，再运行 `lab.scenario_site:create_app`；配置固定目标、服务身份和 B 投影。**不要用旧站的状态文件或固定目标启动第二控制器。** Lab 重建与采集约定见 [SignalLens Lab](https://github.com/catdogrennie-gt/SignalLens-Lab)，新场景的完整链路仍以本轮验收记录为准。

**A 当前是单控制器服务，不能把同一测试目标同时交给蓝、绿两个控制器。** 网关可以切换网页访问，但不能替控制器转移负载所有权。优先只发布可独立更新的网页和已验收场景目录；涉及控制器代码时，需先拆分网页与控制器，或安排明确的释放、停止旧所有者、启动新所有者流程。当前尚不能宣称 A 控制器升级已经实现无中断双版本切换。

启动或更新后依次检查：B ready、演示只读登录、四个页面和静态资源、来源采样、worker 心跳、A 开关/清理与 B 自主任务。不要因为服务进程存在就宣布环境正常。

## 9. 版本发布和回退

开发验证使用独立环境。运行中的源码和前端构建不能原地覆盖。发布时固定后端提交，封存前端，先检查新 API，再经固定网关切换；失败保留旧路由，旧进程和旧静态资源保留用于回退。

B 的读取入口与 A 的控制器生命周期分别验收。B 可并行准备新 API 并切路由；A 不因采用同一网关就可以启动第二所有者。即使新网页已可访问，也要保留“负载控制器尚未切换”的实际状态。

详细步骤、参数与可运行示例见[版本发布与回退](deployment-releases.md)。固定入口只对安全读取做短重试，登录或开关写请求不会被代理自动重复执行。遇到连接错误先查询会话/开关实际状态，再决定是否重试。

首次引入网关会生成新公网地址，旧两站保持在线；检查新入口后才更新公开链接。发布工具不执行数据库迁移；结构变化需提前验证与旧版本兼容，不在切流量时突然破坏旧版。

## 10. 按场景持续验证和发布

每 30 分钟的持续执行采用[单问题演进规范](superpowers/specs/2026-11-13-continuous-evolution-design.md)，在[进度状态](evolution-status.md)接续当前步骤。每轮先检查公开可用性及数据/架构门槛，再推进一个可验证改进；每次实际故障还要独立确认确实产生预期变化。周期不是重复开故障的定时器，也不重置单场景约 60 分钟的时限。

每个场景单独完成下面的闭环；**一个场景验收通过就可以单独开放，不必等整批场景完成**。未验证和失败场景保留在清单中，不能用“代码已实现”替代实际效果。

**先检查证据，再制造问题。** 明确本轮要判断的现象和原因，列出需要的监控项、日志或诊断快照；核对是否已采集、时间是否新鲜、单位和权限是否正确，并预演自然取数、发现、分析与恢复路径。缺项能从现有 Zabbix 接入时先补齐，关键前提无法满足则跳过。每轮只处理一个场景，每 30 分钟检查方向、进度及公开页面可用性；单场景原则限时一小时，过久无结果则记录阻碍后暂停。

**分别核对三种周期：** 数据采集、信号检查与 AI 分析并非同一个计时器。加快采样不代表 AI 会更快运行；预演时要确认实际分析时间、剩余预算和自然派发路径。临时加速结束后必须读回原周期。租约到期后的恢复依赖存活后台执行清理，不能只等过期时间就宣称已还原。

**修改数据选择后：** 新自主任务保存当时所选的来源和监控项，冻结及取证时复核版本；选择变化会停止旧任务，由后续巡检依据新选择创建任务。新分析不会再混入已移除项，仍选中的兼容历史可作为基线。已经生成的历史报告和清单保持原样，查看时仍以原冻结窗口为准。

**阅读快照报告时：** 模型只看到本次保留的授权采样。两份非空快照不是两次事故，一份非空快照也不能证明全窗口仅发生一次；缺少同来源后续空采样不能声称恢复。平台按来源、主机和监控项区分时间关系，优先保留最早及最新异常快照；关键依据无法在预算内保留时明确失败，不用删掉关键依据后的结论代替。

1. **列清单**：写清工作中常见的现象、需要哪些已采数据，以及当时 Zabbix 的模板、宏、触发器和告警覆盖。先判断本场景要验证新增发现、提前线索，还是已有告警的解释增强。
2. **可控复现**：先记录正常基线，再在独立测试目标施加有界负载，保留开始、结束和清理证据；不向平台输入预期答案。
3. **检查平台表现**：核对实际取数、是否自主发现、结论是否成立、原因是否有引用、建议是否可执行。把缺数据、调度失败、误判、解释不充分分别记录，不只记录“出了一份报告”。
4. **补覆盖缺口**：根据实际失败改采集、处理、检查或解释逻辑；缺失证据仍标未知，不能靠改结论文字掩盖数据缺口。
5. **重测**：重新跑正常、故障和恢复，必要时加入相似但不同原因的反例，确认改动没有只记住某个固定脚本。
6. **逐项发布**：在验证清单登记版本、实际结果、限制及证据位置，同时更新本手册。仅发现、分析、恢复与展示均验收通过的场景才公开；待验证或诊断失败的场景留在内部，不作为访客演示。发布后复查公网入口、只读权限和回退路径。

验证状态为未知或失败时，必须写明**卡在哪一环、已有证据、下一步改什么、怎样重测**，保持场景未开放，并在内部标为待验证。数据不足不是健康，关闭负载也不自动代表恢复验收通过。

开始下一个案例前，先写 **信息需求 → 接入与有效性检查 → 自然流程预演 → GO / SKIP**：检查已选数据、实际采样时效、单位与标签语义、时间配对及读取/外发权限；预演正常采样、自主发现、冻结分析、关闭和恢复，以及临时加速能否按期还原。关键条件不能补齐时记录缺项并标 `SKIP`，保持开关关闭；这些条件通过后才允许 `ON`，不能边制造问题边猜需要什么数据。

**证据校验提示：** 新采集内容入库后才封存校验值，冻结报告也按实际读回的内容生成清单。若旧证据出现 `evidence_payload_checksum_unverifiable`，表示内容无法按原校验值核验；新清单会排除它并注明数据缺口，不能据此判断正常，也不能直接认定人为篡改。必需引用不符时停止建立新清单并返回 409。维护时先检查采集版本和新样本的一致性，保留旧记录，不批量重算旧哈希或改写旧报告。

## 采集缺口应该从哪里查看

实验验证过的例子见[采集错误与恢复](validation/data-quality-01.md)：一个来源提取失败时，应查看具体不可用项，不能继续引用旧正常值判断当前健康；恢复须等新采样到达。该实验对象现已暂停归档，原正常监控项保留，不是可公开触发的数据库故障。

首页只有在存在具体缺口时才提示，点击 **查看缺失明细** 在原处展开：逐项列出对象、监控项、最近样本、缺样本/过期/停用等原因和补齐建议。不会把未选择的文本或日志类型当成必需项，也不会把你直接送到接入页。

“查看该对象的数据”只打开对应对象的数据页。顶部业务和时间选择保留；缺口列表表示当前采集元数据状态，不等于所选历史窗口完整或数据库健康。报告页“报告覆盖与限制”来自该报告自己的冻结结果，不拿当前对象配置替代旧报告的依据。只读用户可以查看这些信息，补采与配置修改仍由维护者处理。

## 分析失败时如何判断

**先核对执行组件。** 定时发现和自动派发在采集后台运行，AI 后台只领取队列任务；只更新网页、API 或 AI 进程，不代表自动检查采用了新逻辑。当前四个组件均已交接至封存16。17:28 自然检查已写入异常额度保留状态，但下一次到期拒派、跨日及新异常仍需分别验证。网关磁盘配置已同步，完整电脑重启恢复未验，不应直接调用旧桌面入口替代当前部署。详见[交接验收](superpowers/specs/2026-11-13-scheduler-rollout-correction-design.md)。

**周期检查与异常分析的日次数（封存 16）：** 启用异常分析、每日上限至少为 2 时，系统在原上限内预留向上取整的 20% 给异常分析；例如 12 次中，周期与手动综合检查合计最多 9 次。达到普通份额会显示“等待异常分析”并说明原因，信号检查继续运行；总次数用尽仍明确显示预算已耗尽。失败和旧策略版本的派发也计数，重启、修改配置、重复点击不清零。1 次策略或关闭异常分析不预留。新算法不能补回当天已经用掉的次数，也不保证某次触发立即取得报告。实际范围见[分配设计与验收](superpowers/specs/2026-11-13-anomaly-budget-design.md)。

**次数用尽与数据未选要分开处理。** 在接入页可查看“业务 A · 请求与连接容量”的池容量、占用、排队及请求/数据库数据；该新增对象目前只准备采集，没有自主模型策略。原业务 A 的分析策略日派发已达上限，不能靠重复开关产生新报告，也不能把数据已入库写成诊断通过。其常态 AI 巡检已从五分钟改为一小时，异常信号仍五秒检查；日次数未重置，未来效果待观察。完整边界见[POOL-01](validation/pool-01-data-prerequisites.md)。

先区分等待派发、排队、准备证据、调用模型与完成报告。没有有效报告时不能显示为已确认健康；结构重试最多一次，仍有预算、授权、期限和引用校验。`model_call_outcome_unknown` 表示请求费用或结果不能确定，不会自动重发。先看原任务和审计状态，不反复点击分析或开故障碰运气。
