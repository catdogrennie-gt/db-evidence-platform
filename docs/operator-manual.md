# 操作手册

这套平台把 Zabbix 已有的数据放在一起，持续检查数据库与关联应用的状态。日常先看问题结论，需要核实时再看曲线和证据；处理建议由人判断和实施，AI 不执行 SQL、Shell 或数据库变更。

本手册随功能维护。**页面实现、实验负载实现、平台实际发现并正确解释，是三个不同的完成状态。** 新场景是否验证通过，以[场景验证清单](validation-scenarios.md)及其实际记录为准；本手册中的启动示例不是“任意机器部署已经通过”的承诺。

## 1. 先选入口和身份

| 入口或身份 | 可以做什么 |
| --- | --- |
| B 完整平台：演示只读访客 | 查看授权演示业务的对象、指标、问题、报告、来源摘要、巡检与配置状态；不能保存配置或触发任务 |
| B 完整平台：运维维护者 | 在授权业务范围内连接来源、组合数据、配置巡检和阅读结果；管理权限与数据权限分别授予 |
| A 快速功能演示 | 免登录，选择已开放的固定场景、开启/关闭有界测试负载，查看 B 的实际结果 |

当前公网入口和演示账号见[README](../README.md#在线体验)。新安装使用本机单独生成的账号，不能把公开演示口令作为自己的管理员密码。

B 的四个主要页面：**问题分析 → Zabbix 接入 → 数据查看 → 配置**。顶部业务筛选与时间范围影响当前查看，**不会自动改写后台巡检策略**。只读用户看到“可查看，不可操作”是正常状态；只读不表示只能看首页，凭据和内部连接地址仍不公开。

## 2. 首次接入 Zabbix

这一步由具备来源管理和相应业务授权的人操作；访客可以跳到第 5 节。

1. 先在 Zabbix 配好实际数据库、服务器和应用采集，检查最新样本。数据库和主机优先沿用官方模板，模板不足的诊断信息仍经 Zabbix 扩展采集。
2. 在 Zabbix 创建独立只读身份及 API Token，只开放需要分析的主机组。不要提供 Zabbix 管理员凭据或业务数据库口令给平台。
3. B 打开 **Zabbix 接入**，选择 **连接只读 Zabbix**，填写来源名称、API 地址、所属业务系统、只读 Token 与允许主机组。
4. 保存后核对来源状态、可见主机和最近成功时间。连通只证明 API 可访问，不能证明 SQL、日志或每项诊断信息都已经采到。

已有对象的来源不要改指另一套 Zabbix；不同来源另建。平台不会自动安装 Agent、创建数据库账号或改上游模板。采集准备参见[官方模板与扩展说明](zabbix-official-setup.md)。

## 3. 勾选数据，组成联合分析对象

在 **Zabbix 接入 → 新建联合分析对象** 按向导操作：

| 步骤 | 怎么填写、怎么核对 |
| --- | --- |
| 定义范围 | 选择一个 Zabbix 来源，写清业务名称和分析目标，设置平台取数周期 |
| 选择数据 | 按主机、监控项名称/key、主机标签或监控项标签过滤，勾选需要一起分析的具体项目 |
| 登记关系 | 可选登记“应用连接数据库”“数据库运行于主机”等关系，帮助理解对象；登记关系不是已证明的因果 |
| 核对保存 | 核对主机、1–32 个监控项、单位、值类型和采样状态，点击 **保存联合对象** |

一个联合对象来自同一 Zabbix 来源和业务系统；只包含勾选项，不自动加入主机上的所有数据。筛选和翻页保留已选内容。未知 key 也可选择，不用先把数据强行归类成平台预设的数据库类型。

建议围绕问题选数据，而非把所有指标塞满：应用请求耗时、数据库调用耗时、连接池/排队，配合数据库连接余量、SQL 代价、主机资源和必要诊断信息。数值能绘图；文本与日志保留原含义，访问原文仍需敏感读取授权。

保存后先点 **查看数据**：核对 **数值图表**、**原始历史 / 文本与日志**、**组成与登记关系**，确认时间、单位和数据缺口，再配置巡检。没有采样的项可以保存等待采集，但不能当成正常值。

## 4. 配置自主巡检

维护者进入 **配置 → 巡检**，选择需要持续检查的联合对象，设置模式、周期和模型预算，保存并启用。

- **确定性规则**：只做程序检查，不调用外部模型。
- **脱敏 AI 综合分析**：需要模型配置、业务数据权限和明确外发授权；模型关联当次获准证据，提出解释和建议。
- **检查周期**与**综合巡检周期**不同；平台取数周期还与 Zabbix 上游采样周期不同。上游没有新样本，提高平台频率也不会生成新数据。
- 后台按策略运行，不要求网页常开。周期综合分析不以“Zabbix 已发告警”为唯一前提。

指标变化筛查会保留首次有效稳定采样作为对照，按来源、监控项及配置版本隔离。它只是实测参考，不等于健康基线；没有合格参考时不强行判断。业务长期改变后，由维护者确认并刷新联合对象配置，等待新参考形成。不要反复改配置来消除真实异常，历史证据和报告仍需核对。

启用后核对最近检查、下一次计划、实际任务状态和最近完成时间。没有新报告时先查来源、策略、队列、权限、外发许可和预算，不能用反复点主动分析代替检查调度问题。**规则或模型发现的线索不等于根因已确认。**

## 5. 日常读问题与证据

进入 **问题分析**，先核对业务范围、巡检状态和覆盖缺口，打开需要关注的问题：

1. 先读摘要：**发生了什么 → 直接原因/关联原因 → 当前结论 → 建议怎么做**。
2. 核对它是实际观察、规则线索还是 AI 待核验解释。信息不足、无法确认和被反证都应保留，不能只看模型语气是否肯定。
3. 需要时展开分析过程，查看引用的数值、趋势图、登记关系、支持/反对依据以及缺少的信息；并非每份报告都必须有拓扑图或联合根因。
4. 核对报告的对象、时间窗和来源。旧报告保留当时证据，不会随着现在的数据自动改变；跳到 **数据查看** 查询的是所选新窗口。
5. 由人员决定是否处理，再用后续实际采样核验。模型写了“恢复”或任务显示 completed，都不能代替恢复证据。

有数据而没有 Zabbix 告警，可能是尚未满足当前阈值，也可能需要关联多个指标。验证新增发现时要同时核对**当时的模板、宏、触发器和实际事件**；不能为了证明平台价值而关闭 Zabbix 告警。若上游已有告警，本次价值应记为补充解释，而非新增发现。

## 6. A 多场景快速演示

打开 A 后先看场景目录的状态。**实现待完整验证**表示负载代码可用，尚不等于平台已正确发现并解释；**尚未实现**的场景不能启动。当前配置了 SQL 效率、连接池、临时表、应用排队反证、长读视图和副本业务读陈旧六项实际测试负载与采集。前三项已完成自主发现和恢复核对，分析仍有待完善之处；后三项仅完成直接负载与清理，尚待完整平台验证。具体状态以页面和验证清单为准。

页面每 **60 秒**更新内容，保持已展开内容与浏览位置；需要立即查看时点手动刷新。刷新网页数据不会加速上游采样，也不会发起一次 AI。

先读每项的**业务表现 → 本次Zabbix告警对照 → 平台发现线索**。没有对应告警，可能是尚未达到实际阈值、缺少联动规则，也可能是采集失效；这三种情况不能混写。上游已有告警时，本平台展示的是额外的关联解释。预设说明是演示背景，真实结果以当轮报告和引用为准。标为“发现与恢复已验证 · 分析待完善”的场景，表示工作流成立，不能当成根因诊断验收；下方“上次人工核对的实测”属于历史验证记录，不是当前实时值。

1. 选一个可用场景，点击 **开启问题**。所有访客共享同一开关，同一时刻最多一个场景生效，重复开启不叠加负载。
2. 看 **平台正在做什么** 中的实际取数周期、检查周期、最近检查与任务状态。A 会临时申请加快 B 的检查，界面刷新不等于重新调用一次 AI。
3. 看 **发现与分析** 及 **当前监控 · 实际采样**，必要时进入 B 阅读完整报告。A 不创建调查、不调用模型，也不把预期答案交给 B。
4. 点击 **关闭问题**，先确认负载控制状态，再等待后续实际样本恢复。关闭网页不会主动关闭实验；控制服务失联后由短租约停止负载。
5. 目录切换只改变本页查看，不会自动切换共享故障。要换一个问题，先关闭当前故障，再选择并开启新场景。若仍显示正在释放、不可用或错误，先核对清理结果，不通过增加连接或重复发任务强行推进。

开关没有次数、冷却或“必须等待监控确认恢复才能再次打开”的操作门槛。模型调用仍遵守平台自己的预算和去重策略。**负载已关闭、数据库直接清理完成、Zabbix 已采到恢复、旧报告内容，分别看待。**

## 7. 遇到空白、未知或失败

| 看到的情况 | 先检查什么 |
| --- | --- |
| 来源连通但没有数据 | 允许主机组、选中的具体项、窗口、history 保存与 item 是否 unsupported |
| 图表没有新点 | 上游采样/心跳、实际采样时间和缺口；不能补零或用旧值伪装当前正常 |
| 有数据库数据但没有应用信息 | 是否已经在 Zabbix 采应用并选入同一对象；平台不会凭空补出应用指标 |
| 页面显示当前没有问题 | 最近是否真的完成有效巡检，是否有覆盖缺口；没有结果不等于健康 |
| AI 排队、失败或未运行 | 模式、授权、模型可用性、预算和后台 worker；保留失败，不用规则冒充新 AI 报告 |
| 报告是历史结果 | 对照报告冻结窗口和当前观察，不把上次完成时间当成本轮完成 |
| A 显示连接中断或状态过期 | 先查服务和最近成功接收时间；连接断开不是数据库恢复的证据 |
| 访客不能查看某部分 | 核对业务范围和只读投影；原文、凭据或非演示业务仍可能被限制 |
| 保存操作报版本冲突 | 重新读取最新配置，不覆盖其他人的范围或策略修改 |

## 8. 维护者启动与恢复

以下是**已经初始化好独立控制库和私密配置后**的源码约定示例。首次安装、建库、迁移与账号生成按[部署说明](platform/07-operations.md)进行；不要用初始化命令覆盖已有环境。

在对应后端版本目录、使用该版本依赖环境，分别启动 API、取数 worker 和 AI worker：

```powershell
$env:DBA_PLATFORM_CONFIG='D:\Private\DBEvidence\config.json'
python -m uvicorn platform_app.api:create_app --factory --host 127.0.0.1 --port 18480 --no-access-log
```

```powershell
python -m platform_app.worker --config D:\Private\DBEvidence\config.json
python -m platform_app.ai_worker --config D:\Private\DBEvidence\config.json
```

API 与两个 worker 是独立进程，上述前台命令分别在终端/受控服务管理器中运行。私密配置的端口、schema 和运行目录必须匹配此环境。恢复时先核对 VM、Zabbix、控制 MySQL 和 API ready，再查后台心跳；不要重建数据目录或直接按一个旧 PID 杀进程。

A 的多场景站在单独的 Lab 版本目录使用 `SCENARIO_SITE_CONFIG` 指向仓库外配置，再运行 `lab.scenario_site:create_app`；配置固定目标、服务身份和 B 投影。**不要用旧站的状态文件或固定目标启动第二控制器。** Lab 重建与采集约定见 [SignalLens Lab](https://github.com/catdogrennie-gt/SignalLens-Lab)，新场景的完整链路仍以本轮验收记录为准。

**A 当前是单控制器服务，不能把同一测试目标同时交给蓝、绿两个控制器。** 网关可以切换网页访问，但不能替控制器转移负载所有权。优先只发布可独立更新的网页和已验收场景目录；涉及控制器代码时，需先拆分网页与控制器，或安排明确的释放、停止旧所有者、启动新所有者流程。当前尚不能宣称 A 控制器升级已经实现无中断双版本切换。

启动或更新后依次检查：B ready、演示只读登录、四个页面和静态资源、来源采样、worker 心跳、A 开关/清理与 B 自主任务。不要因为服务进程存在就宣布环境正常。

## 9. 版本发布和回退

开发验证使用独立环境。运行中的源码和前端构建不能原地覆盖。发布时固定后端提交，封存前端，先检查新 API，再经固定网关切换；失败保留旧路由，旧进程和旧静态资源保留用于回退。

B 的读取入口与 A 的控制器生命周期分别验收。B 可并行准备新 API 并切路由；A 不因采用同一网关就可以启动第二所有者。即使新网页已可访问，也要保留“负载控制器尚未切换”的实际状态。

详细步骤、参数与可运行示例见[版本发布与回退](deployment-releases.md)。固定入口只对安全读取做短重试，登录或开关写请求不会被代理自动重复执行。遇到连接错误先查询会话/开关实际状态，再决定是否重试。

首次引入网关会生成新公网地址，旧两站保持在线；检查新入口后才更新公开链接。发布工具不执行数据库迁移；结构变化需提前验证与旧版本兼容，不在切流量时突然破坏旧版。

## 10. 按场景持续验证和发布

每个场景单独完成下面的闭环；**一个场景验收通过就可以单独开放，不必等整批场景完成**。未验证和失败场景保留在清单中，不能用“代码已实现”替代实际效果。

1. **列清单**：写清工作中常见的现象、需要哪些已采数据，以及当时 Zabbix 的模板、宏、触发器和告警覆盖。先判断本场景要验证新增发现、提前线索，还是已有告警的解释增强。
2. **可控复现**：先记录正常基线，再在独立测试目标施加有界负载，保留开始、结束和清理证据；不向平台输入预期答案。
3. **检查平台表现**：核对实际取数、是否自主发现、结论是否成立、原因是否有引用、建议是否可执行。把缺数据、调度失败、误判、解释不充分分别记录，不只记录“出了一份报告”。
4. **补覆盖缺口**：根据实际失败改采集、处理、检查或解释逻辑；缺失证据仍标未知，不能靠改结论文字掩盖数据缺口。
5. **重测**：重新跑正常、故障和恢复，必要时加入相似但不同原因的反例，确认改动没有只记住某个固定脚本。
6. **逐项发布**：在验证清单登记版本、实际结果、限制及证据位置；已通过项才进入公开演示，同时更新本手册。发布后复查公网入口、只读权限和旧入口连续性。

验证状态为未知或失败时，必须写明**卡在哪一环、已有证据、下一步改什么、怎样重测**，并保持场景未开放或明确标为待验证。数据不足不是健康，关闭负载也不自动代表恢复验收通过。
